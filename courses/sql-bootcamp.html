Overview of Databases

Databases solve the scalability and integrity limitations of spreadsheets by enforcing data types per column and supporting concurrent multi-user access to massive datasets.

A database is a system that allows users to store, organize, and retrieve data efficiently. While spreadsheets (Excel, Google Sheets) work for small datasets, they break down at scale due to limitations in size, data type enforcement, and multi-user access. Databases overcome these constraints through structured storage with enforced column-level data types, support for millions of rows, and concurrent access by multiple users without corruption. SQL (Structured Query Language) is the programming language used to communicate with these database systems. PostgreSQL is one of the most popular open-source relational database management systems, offering robust features, standards compliance, and wide industry adoption.

A spreadsheet is like a small notebook where you write things down. A database is like a giant, organized filing cabinet that many people can use at the same time without messing up each other's pages.

  • Databases enforce data types per column, preventing mixed data (e.g., text in a numeric column)
  • Spreadsheets hit practical limits around 1 million rows; databases handle billions
  • SQL is platform-agnostic: learn it once, use it on PostgreSQL, MySQL, Oracle, etc.
  • PostgreSQL is free, open-source, and widely used in industry
  • Databases support multiple concurrent users without data corruption

Introduction to JOINs

JOINs are the mechanism for combining data from multiple tables, with different JOIN types determining how unmatched rows are handled.

JOIN operations allow the combination of rows from two or more tables based on a related column between them. The various JOIN types (INNER, LEFT OUTER, RIGHT OUTER, FULL OUTER, and UNION) differ in how they treat rows that exist in one table but not the other. Understanding one JOIN type makes the others progressively easier to learn.

Imagine you have two lists of friends: one from school and one from your neighborhood. JOINs are different ways of combining those lists depending on whether you want only friends on both lists, everyone from one list, or everyone from both.

AS Statement

The AS keyword creates column aliases for readability in output, but because it executes last in query processing order, aliases cannot be referenced in WHERE or GROUP BY clauses.

The AS clause assigns an alias (alternative display name) to a column or expression in the result set. This is purely cosmetic for the output; it does not rename the underlying column in the database. A critical nuance is execution order: AS is processed at the very end of a query, after WHERE, GROUP BY, and HAVING have already been evaluated. Therefore, attempting to reference an alias in a WHERE or GROUP BY clause produces an error. The alias only exists in the final display output.

AS is like putting a name tag on your answer. If your math answer is 42, you can label it 'the meaning of life.' But the label only shows up at the end; you cannot use the label while you are still doing the math.

  • AS renames columns/expressions only in the output display, not in the database
  • Especially useful for aggregation results: SUM(amount) AS total_revenue
  • Cannot use aliases in WHERE, GROUP BY, or HAVING (execution order limitation)
  • Alias assignment is optional; omitting AS still works in some contexts but reduces clarity
  • AS is processed last in SQL's logical execution order

📚 Quick Check

Why does this query fail: SELECT SUM(amount) AS total FROM payment WHERE total > 100?

SQL processes WHERE before AS in its logical execution order. The alias 'total' has not been created yet when WHERE runs, so PostgreSQL cannot find it.

What does the AS clause actually modify?

AS only changes the column header shown in query results. It does not alter the underlying database schema, data types, or table definitions.

Which SQL clause CAN reference an alias created with AS?

ORDER BY is processed after the SELECT clause (where AS is defined), so it can reference aliases. WHERE, GROUP BY, and HAVING are processed before SELECT.

Inner Joins

An INNER JOIN returns only rows where the join condition finds a match in both tables, discarding any row that exists exclusively in one table.

The INNER JOIN is the most fundamental JOIN operation in SQL. It combines rows from two tables by matching values in a specified column pair, returning only those rows where a match exists in both tables. Rows present in only one table are excluded from the result entirely. The operation is symmetrical: swapping table order produces the same result set. The join condition (specified after ON) defines which columns to compare for matching. In practice, this is typically a foreign key relationship (e.g., customer_id in an orders table matching id in a customers table).

Imagine two attendance lists: one for who signed up for a field trip and one for who actually showed up. An INNER JOIN gives you only the kids who did both: signed up AND showed up.

  • INNER JOIN returns ONLY rows with matches in both tables
  • Rows exclusive to either table are silently dropped from results
  • Table order is irrelevant for INNER JOIN (symmetrical operation)
  • The ON clause specifies which columns to match between tables
  • INNER JOIN is the default; writing just 'JOIN' implies INNER JOIN
  • Most common real-world use: linking tables via foreign key relationships

📚 Quick Check

What happens to rows in Table A that have no matching row in Table B during an INNER JOIN?

INNER JOIN only returns rows where a match exists in both tables. Unmatched rows from either table are silently dropped.

Does changing the table order in an INNER JOIN affect the result set?

INNER JOIN is symmetrical: A INNER JOIN B produces the same row set as B INNER JOIN A. Only column order in output may differ.

What keyword can be omitted since INNER JOIN is the default?

Writing just 'JOIN' without the INNER keyword defaults to INNER JOIN in PostgreSQL and most SQL implementations.

Full Outer Joins

A FULL OUTER JOIN returns every row from both tables, filling in NULLs wherever one side has no match, making it the most inclusive JOIN type.

The FULL OUTER JOIN combines all rows from both tables regardless of whether a match exists. Where a match is found, columns from both tables are populated normally. Where no match exists (a row is exclusive to one table), the columns from the other table are filled with NULL. This makes FULL OUTER JOIN the most inclusive join type, equivalent to the union of a LEFT JOIN and a RIGHT JOIN. It is symmetrical: table order does not affect which rows appear. An additional variant adds a WHERE clause filtering for NULLs on both sides, which returns only rows exclusive to one table or the other (the set difference).

Imagine combining two birthday party guest lists. FULL OUTER JOIN means EVERYONE from both lists shows up on the final list. If someone was only invited to one party, they still appear, but with a blank space where the other party info would be.

  • Returns ALL rows from both tables, matched and unmatched
  • Unmatched rows get NULL in the columns from the other table
  • Symmetrical: swapping table order does not change the result
  • Adding WHERE TableA.id IS NULL OR TableB.id IS NULL gives rows exclusive to one table
  • Most inclusive JOIN: no data is ever dropped
  • Useful for finding orphaned records or data discrepancies between tables

How does FULL OUTER JOIN differ from INNER JOIN?

INNER JOIN discards unmatched rows entirely, while FULL OUTER JOIN preserves all rows from both tables, using NULL for missing matches.

What does adding WHERE A.id IS NULL OR B.id IS NULL to a FULL OUTER JOIN achieve?

This WHERE clause filters out the matched rows (center of the Venn diagram), leaving only rows that exist exclusively in Table A or exclusively in Table B.

Left Outer Join

A LEFT JOIN preserves every row from the left (first) table and fills NULLs for right-table columns where no match exists, making table order significant.

The LEFT OUTER JOIN (commonly written as LEFT JOIN) returns all rows from the left table (the table listed first in the FROM clause), regardless of whether a matching row exists in the right table. Where a match is found, columns from the right table are populated normally. Where no match exists, right-table columns contain NULL. Unlike INNER JOIN, LEFT JOIN guarantees that no rows from the left table are lost. Adding a WHERE clause filtering for NULL on the right table's key column isolates rows exclusive to the left table (present in left, absent in right). Table order matters: swapping tables changes the result set.

Imagine you have your friend list and a list of people who came to your party. LEFT JOIN keeps ALL your friends on the final list, but marks the ones who did not come with a question mark.

  • All rows from the LEFT table appear in results, guaranteed
  • Right-table columns show NULL where no match exists
  • Table order matters: A LEFT JOIN B is different from B LEFT JOIN A
  • WHERE right_table.key IS NULL isolates left-only rows
  • LEFT JOIN and LEFT OUTER JOIN are identical (OUTER is optional)
  • Most common use case: find records in one table missing from another

Right Joins

A RIGHT JOIN is functionally identical to a LEFT JOIN with the tables swapped; it exists for readability but is rarely used in practice.

The RIGHT OUTER JOIN (or RIGHT JOIN) returns all rows from the right table (the second table listed) and matching rows from the left table. Where no match exists in the left table, those columns contain NULL. It is the mirror image of LEFT JOIN: any RIGHT JOIN query can be rewritten as a LEFT JOIN by simply swapping the table order in the FROM clause. In practice, most SQL developers exclusively use LEFT JOIN for consistency and readability, making RIGHT JOIN relatively uncommon in production code.

RIGHT JOIN is the same as LEFT JOIN, just looking at it from the other side. It is like saying 'everyone on my RIGHT hand list is included' instead of 'everyone on my LEFT hand list.'

  • RIGHT JOIN = all rows from the right (second) table preserved
  • Left-table columns show NULL where no match exists
  • Functionally identical to LEFT JOIN with tables swapped
  • Rarely used in practice; LEFT JOIN is the industry standard
  • RIGHT JOIN and RIGHT OUTER JOIN are synonymous

UNION

UNION vertically stacks the results of two SELECT statements (like gluing tables top-to-bottom), unlike JOINs which combine tables side-by-side on matching columns.

The UNION operator concatenates the result sets of two or more SELECT statements vertically. Unlike JOINs, which combine tables horizontally by matching column values, UNION stacks rows from separate queries on top of each other. The SELECT statements must return the same number of columns with compatible data types. By default, UNION removes duplicate rows; UNION ALL preserves all duplicates. UNION is ideal for combining data split across multiple tables with identical schemas (e.g., quarterly sales tables, regional data).

JOINs are like putting two puzzle pieces side by side. UNION is like stacking two decks of cards on top of each other into one tall pile.

  • UNION stacks results vertically (rows appended), not horizontally (columns merged)
  • Both SELECT statements must have the same number of columns with compatible types
  • UNION removes duplicate rows by default
  • UNION ALL keeps all rows including duplicates (faster, no dedup overhead)
  • ORDER BY can be applied after the final UNION to sort the combined result

📚 Quick Check

What is the key difference between UNION and UNION ALL?

UNION performs a deduplication pass on the combined results. UNION ALL skips deduplication, keeping all rows and running faster.

When should UNION be used instead of a JOIN?

UNION is for vertical concatenation of identically-structured result sets. JOINs are for horizontal combination based on matching keys.

CASE

CASE is SQL's inline IF/ELSE mechanism that creates computed columns by evaluating conditions row-by-row, and becomes especially powerful when wrapped in aggregate functions like SUM or COUNT for conditional counting.

The CASE expression provides conditional logic within SQL queries, functioning as an inline IF/ELSE block. It evaluates conditions sequentially for each row and returns the result of the first matching condition. Two syntax forms exist: (1) the General CASE, which evaluates arbitrary boolean conditions (WHEN condition THEN result), and (2) the CASE Expression, which compares a single column against multiple values (CASE column WHEN value THEN result). The ELSE clause handles all unmatched conditions. CASE becomes most powerful when combined with aggregate functions: wrapping CASE in SUM (with THEN 1 ELSE 0) enables conditional counting, allowing multiple category counts to appear as separate columns in a single query result.

CASE is like a sorting hat for each row of data. It looks at each row and says 'if you are THIS, go in the red bucket; if you are THAT, go in the blue bucket; otherwise, go in the grey bucket.'

  • General CASE: WHEN condition THEN result (arbitrary boolean logic per condition)
  • CASE Expression: CASE column WHEN value THEN result (shorthand for single-column comparison)
  • ELSE handles all conditions not matched by any WHEN clause
  • END keyword is mandatory to close a CASE block
  • SUM(CASE WHEN ... THEN 1 ELSE 0 END) creates conditional counts as columns
  • Multiple CASE expressions in one SELECT create side-by-side categorical columns

COALESCE

COALESCE returns the first non-NULL value from its argument list, providing a clean way to substitute default values for NULL without modifying the underlying table data.

The COALESCE function accepts an unlimited number of arguments and returns the first one that is not NULL. If all arguments are NULL, it returns NULL. The primary use case is providing fallback values during calculations involving nullable columns. For example, when subtracting a discount column that may contain NULL from a price, wrapping the discount in COALESCE(discount, 0) ensures NULL discounts are treated as zero without altering the stored data. COALESCE is evaluated at query time and never modifies the underlying table. It can be nested or chained with multiple fallback values for progressively deeper NULL handling.

COALESCE is like a backup plan for missing answers. If the first answer is blank, use the second one. If that is blank too, use the third one. It picks the first answer that actually exists.

  • Returns the first non-NULL argument in the list
  • Does NOT modify the underlying table data
  • Essential for arithmetic involving nullable columns (NULL + number = NULL)
  • COALESCE(discount, 0) treats missing discounts as zero
  • Accepts any number of arguments; evaluates left to right
  • Evaluated at query time; purely a read operation

CAST

CAST converts data between types (string to integer, date to text, etc.) and is essential when SQL operations require compatible types that the stored data does not natively provide.

The CAST function converts a value from one data type to another. The standard SQL syntax is CAST(expression AS target_type). PostgreSQL also supports a shorthand notation using double colons (expression::target_type). The conversion must be reasonable; attempting to cast an alphabetical string to an integer will produce an error. Common use cases include converting string-formatted numbers to integers for arithmetic, converting timestamps to date-only values for grouping, and converting numeric values to strings for concatenation. CAST is essential when working with data that was stored in a suboptimal type or when functions require a specific input type.

CAST is like translating a number written in words ('five') into the actual digit (5). The information is the same, just in a different form that the computer can use differently.

  • Standard syntax: CAST(value AS type)
  • PostgreSQL shorthand: value::type (double colon operator)
  • Conversion must be logically possible (e.g., '5' to integer works, 'hello' to integer fails)
  • Common conversions: VARCHAR to INTEGER, TIMESTAMP to DATE, NUMERIC to TEXT
  • Returns an error (not NULL) if conversion is impossible
  • The :: shorthand is PostgreSQL-specific; CAST() is SQL standard and portable

NULLIF

NULLIF returns NULL when two arguments are equal, making it the standard defense against division-by-zero errors by converting zero denominators into NULL (which produces NULL rather than crashing).

The NULLIF function takes two arguments and returns NULL if they are equal; otherwise, it returns the first argument. Its primary practical application is preventing division-by-zero errors. In SQL, dividing by NULL returns NULL (a safe non-error state), while dividing by zero raises a fatal error. By wrapping the denominator in NULLIF(denominator, 0), any zero value becomes NULL, converting a crash into a graceful NULL result. NULLIF is conceptually the inverse of COALESCE: while COALESCE replaces NULL with a value, NULLIF creates NULL from a specific value.

NULLIF is like a bouncer at a door. It checks if two things match. If they do, it turns the answer into 'nothing' (NULL). Its best trick is catching zeros before they crash a division.

  • NULLIF(a, b) returns NULL if a = b; otherwise returns a
  • Primary use: preventing division-by-zero (NULLIF(denominator, 0))
  • Division by NULL safely returns NULL instead of an error
  • Conceptual inverse of COALESCE (COALESCE fills NULLs; NULLIF creates NULLs)
  • Two arguments only; cannot accept a list like COALESCE
  • Often used with COALESCE: COALESCE(x / NULLIF(y, 0), 0) gives 0 instead of NULL for zero-division

Views

A view is a saved query that behaves like a virtual table, allowing complex multi-table JOINs to be called with a simple SELECT without storing duplicate data.

A view is a named, stored query in PostgreSQL that can be referenced as if it were a table. When a view is queried, the underlying SQL is executed in real-time; no data is physically duplicated. Views encapsulate complex queries (multi-table JOINs, filtered subsets) into reusable building blocks, reducing repetition and errors. Views can be created (CREATE VIEW), replaced (CREATE OR REPLACE VIEW), renamed (ALTER VIEW ... RENAME TO), and deleted (DROP VIEW). They are ideal for frequently-used query patterns, access control (exposing only certain columns), and simplifying complex report generation.

A view is like a saved recipe. Instead of writing down all the cooking steps every time, you just say 'make the recipe' and it does all the steps for you automatically.

  • CREATE VIEW view_name AS SELECT ... saves the query
  • Querying a view: SELECT * FROM view_name (identical to querying a table)
  • Views do NOT store data physically; they re-execute the query each time
  • CREATE OR REPLACE VIEW updates an existing view without dropping it
  • ALTER VIEW ... RENAME TO changes the view name
  • DROP VIEW [IF EXISTS] removes the view

SELECT Statement

SELECT is the foundational retrieval command that specifies which columns to return from a given table, with SELECT * returning all columns at once.

The SELECT statement is the most frequently used SQL command, responsible for retrieving data from database tables. Its basic syntax follows the pattern SELECT column_name FROM table_name, where the database engine first identifies the target table, then extracts the specified column(s). Multiple columns can be selected by separating column names with commas. The wildcard SELECT * retrieves all columns simultaneously, which is useful for exploration but should be avoided in production queries due to performance overhead. SQL keywords are conventionally capitalized (SELECT, FROM) to visually distinguish them from user-defined names, though this is not syntactically required.

Imagine a big filing cabinet (the database) with folders (tables) inside. SELECT is like saying 'open that folder and show me just the name column' or 'show me everything in it.'

  • SELECT column_name FROM table_name is the basic retrieval pattern
  • SELECT * returns all columns from a table
  • Multiple columns are separated by commas: SELECT col1, col2 FROM table
  • SQL reads the FROM clause first to identify the table, then selects columns
  • Capitalizing SQL keywords (SELECT, FROM) is convention, not requirement
  • Avoid SELECT * in production; specify only needed columns for performance

SELECT DISTINCT

DISTINCT eliminates duplicate values from a column's result set, returning only unique entries regardless of how many times each value appears in the table.

When a column contains repeated values, SELECT DISTINCT filters the result to show each unique value exactly once. The syntax is SELECT DISTINCT column_name FROM table_name, with optional parentheses around the column for clarity. DISTINCT operates on the column specified immediately after it. This is particularly useful for understanding the range of categorical values in a dataset (e.g., what rating categories exist, what departments are represented). DISTINCT does not modify the underlying data; it only affects what is displayed in the query result.

Imagine a jar full of colored marbles with lots of repeats. DISTINCT is like pulling out one marble of each color and ignoring all the copies. You just want to know what colors exist.

  • DISTINCT removes duplicate rows from the result set
  • Syntax: SELECT DISTINCT column_name FROM table_name
  • Parentheses are optional: SELECT DISTINCT(column) also works
  • Useful for identifying categorical ranges (ratings, statuses, types)
  • Does not alter the actual table data, only the displayed results
  • Cannot determine if duplicates represent the same entity or different ones with the same value

COUNT

COUNT is an aggregate function that returns the number of rows matching a condition, and it produces the same result regardless of which column is specified because all columns in a table have the same row count.

The COUNT() function is an aggregate that returns the total number of input rows matching a query's conditions. Since every column within a table shares the same number of rows, COUNT(column_name), COUNT(other_column), and COUNT(*) all return identical results. The asterisk convention COUNT(*) is preferred as it clearly communicates 'count all rows.' COUNT becomes significantly more powerful when combined with other keywords: COUNT(DISTINCT column) counts unique values, while pairing COUNT with WHERE filters which rows are counted. Parentheses are mandatory for COUNT since it is a function call, not a keyword.

COUNT is like asking 'how many kids are in this classroom?' It doesn't matter if you count by looking at their shirts or their shoes; you'll get the same number because each kid has both.

  • COUNT(*) returns total number of rows in a table or result set
  • COUNT(column_name) returns the same number since all columns have equal rows
  • COUNT(DISTINCT column) counts only the unique values in that column
  • Parentheses are required: COUNT is a function, not a standalone keyword
  • Most useful when combined with WHERE, DISTINCT, or GROUP BY
  • COUNT alone just answers 'how many rows?' without revealing what those rows contain

SELECT WHERE - Part One

WHERE filters rows based on conditions applied to column values, using comparison operators (=, >, <, >=, <=, <>/!=) and logical operators (AND, OR, NOT) to specify which rows to return.

The WHERE clause restricts the rows returned by a SELECT statement based on specified conditions. Conditions are built using comparison operators (= for equality, > and < for inequality, >= and <=, and <> or != for not-equal) applied to column values. Multiple conditions combine using logical operators: AND requires all conditions be true, OR requires at least one, and NOT negates a condition. The WHERE clause appears after FROM and determines row-level filtering before results are returned. This is the primary mechanism for targeted data retrieval in SQL.

WHERE is like a filter on a search. If you're looking for red shoes under $50 on a shopping website, you're using WHERE: show me shoes WHERE color is red AND price is less than 50.

  • WHERE appears after FROM: SELECT cols FROM table WHERE condition
  • Comparison operators: =, >, <, >=, <=, <> (or !=)
  • Logical operators AND, OR, NOT combine multiple conditions
  • String values must be enclosed in single quotes
  • WHERE filters rows before they appear in the result set
  • Conditions are evaluated for each row independently

ORDER BY

ORDER BY sorts result rows by one or more columns in ascending (ASC, default) or descending (DESC) order, and always appears at the end of a query since it operates on the final result set.

The ORDER BY clause sorts the rows returned by a query based on specified column values. By default, sorting is ascending (ASC); appending DESC reverses the order. Multiple columns can be specified for multi-level sorting: rows are first sorted by the primary column, then ties are broken by the secondary column. ORDER BY must appear at the end of the query (after WHERE, if present) because it operates on the already-filtered result set. Importantly, ORDER BY can reference columns not included in the SELECT list, as it operates after row selection. PostgreSQL allows ordering by column position (ORDER BY 1) but this is discouraged for readability.

ORDER BY is like telling the librarian 'arrange these books by author name A-Z.' If two books have the same author, you can say 'then sort those by title.' It just puts things in order.

  • Default sort is ascending (ASC); use DESC for descending
  • ORDER BY goes at the end of the query, after WHERE
  • Multiple columns: ORDER BY col1 ASC, col2 DESC for tie-breaking
  • Can sort by columns not in the SELECT list
  • Operates on the final filtered result set
  • Numeric column positions work (ORDER BY 1) but named columns are preferred

LIMIT

LIMIT restricts the number of rows returned by a query and is especially powerful when combined with ORDER BY to answer 'top N' or 'bottom N' questions.

The LIMIT clause caps the number of rows in the result set to a specified maximum. It is placed at the very end of a query, after ORDER BY. While LIMIT alone simply truncates results to the first N rows, its real power emerges in combination with ORDER BY: ORDER BY amount DESC LIMIT 5 returns the top 5 highest payments. LIMIT is useful for sampling data during exploration, for pagination, and for answering 'top/bottom N' business questions. LIMIT is not a standard SQL feature (it is PostgreSQL/MySQL specific) but is widely supported; the SQL standard equivalent is FETCH FIRST N ROWS ONLY.

LIMIT is like saying 'just show me the first 5 results.' If you sort from biggest to smallest first, then LIMIT 5 gives you the top 5 biggest.

  • LIMIT N returns at most N rows from the result
  • Goes at the very end of the query (after ORDER BY)
  • Combined with ORDER BY DESC LIMIT N answers 'top N' questions
  • Useful for exploration: LIMIT 5 to preview a large table
  • Not standard SQL but supported in PostgreSQL, MySQL; standard uses FETCH FIRST
  • Without ORDER BY, LIMIT returns arbitrary rows (order not guaranteed)

BETWEEN

BETWEEN provides an inclusive range filter (value >= low AND value <= high) that works with numbers, dates, and timestamps, with special attention needed for timestamp boundary precision.

The BETWEEN operator filters rows where a column value falls within a specified inclusive range. BETWEEN low AND high is equivalent to value >= low AND value <= high. The NOT BETWEEN operator excludes values within the range (exclusive of endpoints). BETWEEN works with numeric values, dates, and timestamps. When used with dates, the ISO 8601 format (YYYY-MM-DD) is required. A critical consideration: when timestamps include time components, BETWEEN may exclude records on the end date if their time is after midnight (00:00:00), since the date string defaults to midnight. This makes careful boundary selection essential for date-range queries.

BETWEEN is like saying 'give me all the books on shelves 3 through 7.' It includes shelf 3 and shelf 7 too (the ends count). NOT BETWEEN means 'skip shelves 3-7, give me everything else.'

  • BETWEEN low AND high is inclusive on both ends
  • Equivalent to: value >= low AND value <= high
  • NOT BETWEEN excludes the range (exclusive of endpoints)
  • Works with numbers, dates, and timestamps
  • Dates must use ISO 8601 format: 'YYYY-MM-DD'
  • Timestamp precision matters: '2007-02-15' means midnight, potentially excluding same-day records with later times

LIKE and ILIKE

Timestamps and Extract - Part One

PostgreSQL offers multiple time data types (TIME, DATE, TIMESTAMP, TIMESTAMPTZ) and functions (NOW, CURRENT_DATE, TIMEOFDAY) for capturing and querying temporal data, with TIMESTAMPTZ being the safest default for future-proofing.

PostgreSQL provides granular time-related data types: TIME (time of day only), DATE (calendar date only), TIMESTAMP (date + time without timezone), and TIMESTAMPTZ (date + time with timezone). The critical design decision when creating tables is whether to include timezone information; TIMESTAMPTZ is recommended because timezone data can always be stripped later, but cannot be retroactively added if never recorded. Built-in functions like NOW() return the current timestamp, CURRENT_DATE returns today's date, CURRENT_TIME returns the current time, and TIMEOFDAY() returns a human-readable string. The SHOW TIMEZONE command reveals the server's current timezone setting.

A database can remember when something happened in different ways: just the date (like a calendar), just the time (like a clock), or both together. The smartest choice is to always save the timezone too, because you can't go back and add it later if you forgot.

  • TIME: stores time of day only (no date)
  • DATE: stores calendar date only (no time)
  • TIMESTAMP: stores date + time without timezone
  • TIMESTAMPTZ: stores date + time with timezone (recommended default)
  • NOW() returns current timestamp; CURRENT_DATE returns today's date
  • Always prefer TIMESTAMPTZ; you can remove timezone later but cannot add it retroactively

Timestamps and Extract - Part Two

EXTRACT() pulls individual date components (year, month, day) from timestamps, AGE() calculates elapsed time, and TO_CHAR() converts timestamps to custom-formatted text strings.

EXTRACT is like pulling apart a date to get just the year, or just the month. AGE tells you how old something is. TO_CHAR makes dates look pretty, like turning '2007-02-15' into 'February 15, 2007'.

  • Combine EXTRACT with GROUP BY for monthly/yearly aggregations

SubQuery

A subquery is a query nested inside parentheses within another query, executing first to produce a result that the outer query then uses for comparison, filtering, or existence checking.

A subquery (or inner query) is a SELECT statement embedded within another SQL statement, enclosed in parentheses. The subquery executes first, producing a result that the outer query uses. Aggregation Functions

Aggregate functions collapse an entire column of values into a single scalar result, and they can only appear in the SELECT or HAVING clauses.

Aggregate functions in SQL accept multiple input values from a column and return a single output value. The five most common aggregate functions are: AVG (returns the arithmetic mean), COUNT (returns the number of rows), MAX (returns the largest value), MIN (returns the smallest value), and SUM (returns the total of all values). These functions operate on the entire column when used without GROUP BY. Important behaviors include: AVG returns a floating-point number with many decimal places (use ROUND to control precision), COUNT(*) counts all rows regardless of column content, and aggregate functions cannot be combined with non-aggregated columns in the SELECT clause without a GROUP BY.

If you have a bucket of numbered balls, aggregate functions answer questions like: what is the biggest number? The smallest? How many balls total? What do they all add up to? They always give back just one answer for the whole bucket.

  • AVG, COUNT, MAX, MIN, and SUM are the five core aggregate functions
  • Aggregate functions can only appear in SELECT or HAVING clauses
  • AVG returns many decimal places; wrap with ROUND(value, decimal_places) to control precision
  • COUNT(*) and COUNT(column_name) both count rows; asterisk is conventional
  • Cannot SELECT a regular column alongside an aggregate without GROUP BY
  • SUM of a column equals AVG times COUNT (mathematical relationship)

GROUP BY - Part One

GROUP BY splits a table into subsets based on shared column values, then aggregate functions independently process each subset to produce one result row per group.

The GROUP BY clause partitions the result set into groups where all rows share the same value(s) in the specified column(s). After grouping, aggregate functions (SUM, COUNT, AVG, etc.) are applied independently to each group, producing one summary row per distinct group. The SELECT clause in a GROUP BY query can only contain: (1) columns listed in GROUP BY, or (2) aggregate function calls. Any column not in the GROUP BY clause and not inside an aggregate function will cause an error. The conceptual execution order is: FROM (identify table) -> WHERE (filter rows) -> GROUP BY (form groups) -> aggregate functions (compute per group) -> HAVING (filter groups) -> SELECT (choose output columns) -> ORDER BY (sort output).

Imagine sorting your toy cars into piles by color. Now you can count how many are in each pile or find the biggest car in each pile. GROUP BY makes the piles; the counting and measuring happen separately for each pile.

  • Each group produces exactly one row in the output
  • SELECT can only include GROUP BY columns or aggregate function calls
  • Without an aggregate function, GROUP BY acts like SELECT DISTINCT
  • Multiple columns in GROUP BY create sub-groups (e.g., per category per region)
  • Execution order: FROM -> WHERE -> GROUP BY -> aggregates -> HAVING -> SELECT -> ORDER BY

Data Types

Selecting the correct data type for each column is a critical design decision that affects storage efficiency, query performance, and data integrity, and should be guided by the documentation rather than guesswork.

Every column in a SQL table must be assigned a data type that defines what kind of values it can store. Overly broad types (e.g., TEXT when VARCHAR(50) suffices) waste storage and weaken validation, while overly narrow types risk truncation or overflow errors.

Data types are like different shaped containers. You wouldn't put soup in a paper bag or a letter in a jar. Each column needs the right container shape so the data fits properly and nothing spills out.

Primary Keys and Foreign Keys

Primary keys uniquely identify rows within a single table, while foreign keys establish referential integrity between tables by pointing to a primary key in another table.

A primary key is a column (or group of columns) that uniquely identifies each row in a table. It must satisfy two invariants: uniqueness (no two rows share the same value) and non-nullability (every row must have a value). Primary keys serve dual purposes: they guarantee row-level identity and provide the anchors for joining tables together. A foreign key is a column in one table that references the primary key of another table, establishing a parent-child relationship. This creates referential integrity: the database guarantees that every foreign key value corresponds to an existing primary key in the referenced table. Attempting to insert a foreign key value that does not exist in the parent table produces an error. This mechanism prevents orphaned records and maintains relational consistency across the schema.

A primary key is like your home address; nobody else has the exact same one, and every house must have one. A foreign key is like writing someone else's address on a letter; it points to a real house that already exists somewhere.

  • Primary keys must be unique AND non-null for every row in the table
  • Primary keys enable JOIN operations by providing reliable matching anchors
  • Foreign keys reference a primary key in another table, creating a relationship
  • Referential integrity prevents inserting foreign key values that don't exist in the parent table
  • A table can have multiple foreign keys pointing to different parent tables
  • Primary keys are typically auto-generated using SERIAL to avoid manual tracking

Constraints

Constraints are declarative rules that enforce data integrity at the database level, preventing invalid data from ever entering the system regardless of how the insertion is attempted.

Constraints are rules enforced on data columns (or entire tables) that prevent invalid data from being stored in the database. They serve as the last line of defense for data integrity, operating at the database engine level rather than relying on application code to validate inputs. Constraints divide into two categories: column constraints (applied to a single column) and table constraints (applied across the entire table). The most common constraints are: NOT NULL (column cannot contain empty values), UNIQUE (all values in a column must be distinct), PRIMARY KEY (combines UNIQUE and NOT NULL for row identification), FOREIGN KEY (values must exist in a referenced table), CHECK (values must satisfy a custom Boolean condition), and EXCLUSION (prevents row conflicts based on specified operators). Column constraints are chosen based on business requirements; there is no universal formula since each table's needs are unique to its domain.

Constraints are like rules at a parking lot. Some spots say 'no parking' (NOT NULL means you must park something there), some say 'one car only' (UNIQUE means no duplicates), and some have height limits (CHECK means the value must meet a condition).

  • NOT NULL: column must always contain a value; rejects rows with missing data
  • UNIQUE: all values in the column must be distinct; rejects duplicates
  • PRIMARY KEY: combines UNIQUE + NOT NULL; identifies rows
  • FOREIGN KEY: value must exist in referenced table; enforces relational integrity
  • CHECK: custom Boolean condition that values must satisfy
  • Column constraints apply to one column; table constraints apply across multiple columns
⚠️ Common Mistakes
Relying on application code alone to validate data without database constraints

Data can enter through multiple paths (APIs, manual SQL, migrations). Only database-level constraints guarantee integrity regardless of entry point.

Always define constraints at the database level as the authoritative enforcement layer

  • ✓ Choose constraints based on business rules: NOT NULL for required fields, UNIQUE for identifiers, CHECK for domain rules
  • ✓ Constraint errors are protective; they prevent corruption rather than causing problems

UPDATE

UPDATE modifies existing column values in-place using SET with optional WHERE filtering, and can pull values from other tables via an UPDATE JOIN pattern or confirm changes with RETURNING.

The UPDATE statement modifies existing data within a table without adding or removing rows. Its syntax uses SET to assign new values to specified columns, optionally filtered by a WHERE clause to target specific rows. Without a WHERE clause, UPDATE affects every row in the table. Three patterns cover most use cases: (1) setting a column to a literal value or function (SET last_login = CURRENT_TIMESTAMP), (2) setting a column equal to another column in the same row (SET last_login = created_on), and (3) the UPDATE JOIN pattern, which pulls values from a different table using FROM and WHERE to match rows. The RETURNING clause appends to any UPDATE to immediately display the affected rows and selected columns, eliminating the need for a follow-up SELECT to verify changes.

UPDATE is like using an eraser and pencil on a filled-out form. You can change what's written in any box without tearing up the whole form and starting over. RETURNING is like the form showing you a preview of what you just changed.

  • Syntax: UPDATE table SET column = value WHERE condition
  • Without WHERE, ALL rows in the table are updated (dangerous in production)
  • SET can use literal values, functions (CURRENT_TIMESTAMP), or other column names
  • UPDATE JOIN: UPDATE tableA SET col = tableB.col FROM tableB WHERE tableA.id = tableB.id
  • RETURNING clause shows affected rows without needing a separate SELECT

DELETE

DELETE removes entire rows from a table based on a WHERE condition, can target rows matching another table via USING, and supports RETURNING to confirm which rows were removed.

The DELETE FROM statement removes entire rows from a table. Unlike UPDATE (which modifies values in-place), DELETE eliminates rows completely. A WHERE clause specifies which rows to remove; without it, all rows in the table are deleted. The USING clause enables deletion based on matches in another table (analogous to the UPDATE JOIN pattern). The RETURNING clause can be appended to display the rows that were actually removed, providing confirmation of the operation. If DELETE is executed against rows that have already been removed (or that don't match the WHERE condition), it returns zero rows affected rather than an error. This idempotent behavior means re-running a DELETE is safe but produces no additional effect. SERIAL sequences do not backfill after deletion; gaps in the sequence remain as indicators of removed rows.

DELETE is like pulling an index card completely out of the filing cabinet and throwing it away. If you try to pull out a card that's already gone, nothing happens; you just get an empty hand.

  • Syntax: DELETE FROM table WHERE condition
  • Without WHERE, ALL rows are deleted (table structure remains, data is gone)
  • USING clause enables deletion based on matches in another table (DELETE JOIN)
  • RETURNING shows which rows were actually removed
  • Re-running DELETE on already-removed rows returns 0 rows affected (no error)
  • SERIAL gaps remain after deletion; IDs are never recycled

ALTER Table

ALTER TABLE modifies an existing table's structure (adding/removing/renaming columns, changing constraints) without destroying and recreating the table or its data.

The ALTER TABLE statement modifies the structure of an existing table. Unlike DROP and CREATE (which destroys and rebuilds), ALTER preserves existing data while changing the schema. Common operations include: ADD COLUMN (adds a new column), DROP COLUMN (removes a column), RENAME COLUMN (changes a column name), RENAME TO (renames the table itself), ALTER COLUMN SET/DROP constraints (modifies column-level rules), and ADD CONSTRAINT (adds table-level constraints). Altering constraints is particularly powerful for evolving schemas. For example, DROP NOT NULL on a column allows NULL values that were previously forbidden, enabling more flexible data entry without data loss. The PostgreSQL documentation serves as the definitive reference for the full range of ALTER TABLE operations, which is extensive.

ALTER TABLE is like remodeling a house while people still live in it. You can add a new room, knock out a wall, or change a room's name without tearing down the whole house and rebuilding from scratch.

  • ADD COLUMN adds a new column with specified type and constraints
  • DROP COLUMN removes a column and all its data permanently
  • RENAME COLUMN old_name TO new_name changes a column's identifier
  • RENAME TO new_table_name changes the table's name entirely
  • ALTER COLUMN ... SET/DROP NOT NULL modifies nullability constraints
  • The original data in other columns is preserved through all ALTER operations

DROP Table

DROP COLUMN permanently removes a column and its associated constraints from a table, with IF EXISTS preventing errors on non-existent columns and CASCADE removing dependent objects.

The DROP COLUMN operation (part of ALTER TABLE) permanently removes a column from a table, along with all its associated indexes, constraints (NOT NULL, UNIQUE, CHECK), and data. However, it does not automatically remove dependent objects like views, triggers, or stored procedures that reference the column; for those, the CASCADE keyword must be added to propagate the removal. Attempting to drop a non-existent column raises an error. The IF EXISTS clause suppresses this error, instead issuing a NOTICE that the column was not found and completing successfully. Multiple columns can be dropped in a single statement. Dropping an entire table (as opposed to just a column) uses DROP TABLE table_name, which removes the table structure and all data permanently.

DROP is like removing a drawer from the filing cabinet forever. IF EXISTS is like saying 'remove drawer 5 if it's there, but don't panic if it's already gone.' CASCADE is like also removing all the labels and signs that pointed to that drawer.

  • ALTER TABLE table DROP COLUMN col removes a column and all its constraints
  • CASCADE additionally removes dependent views, triggers, and stored procedures
  • IF EXISTS prevents errors when dropping a column that may not exist
  • Multiple columns can be dropped in one statement
  • Without IF EXISTS, dropping a non-existent column raises an error
  • DROP TABLE removes the entire table (structure + data); ALTER TABLE DROP COLUMN removes only a column

CHECK Constraint

CHECK constraints enforce custom Boolean conditions on column values at insert/update time, enabling business rules like minimum ages, positive salaries, and cross-column validations directly in the schema.

The CHECK constraint allows creation of custom validation rules beyond the built-in NOT NULL and UNIQUE constraints. A CHECK constraint specifies a Boolean expression that must evaluate to true for any inserted or updated row; if the condition is false, the operation is rejected with an error. CHECK constraints can validate a single column against a constant (salary > 0), compare two columns within the same row (hire_date > birth_date), or enforce date ranges (birth_date > '1900-01-01'). They fire on both INSERT and UPDATE operations. An important side effect: when a CHECK constraint causes a SERIAL insertion to fail, the sequence still increments. This means the next successful insert receives a higher ID than expected, leaving gaps that indicate failed insertion attempts.

CHECK is like a bouncer at a door with a checklist. 'Are you over 21? Is your ticket date after today?' If you don't pass the check, you don't get in, no matter what.

  • CHECK(condition) enforces a custom Boolean rule on each row at insert/update time
  • Can compare a column to a constant: CHECK(age > 21)
  • Can compare two columns: CHECK(parent_age > age)
  • Failed CHECKs still increment SERIAL sequences, leaving ID gaps
  • Multiple CHECK constraints can coexist on different columns in one table
  • CHECK fires on both INSERT and UPDATE operations

CHECK constraint violations cause the entire INSERT operation to fail. No partial row is inserted.

SERIAL gaps can result from both deleted rows and failed INSERT attempts. Each INSERT attempt increments the sequence regardless of success.

CHECK(hire_date > birthdate) ensures the hire date is strictly after the birth date using direct date comparison.
