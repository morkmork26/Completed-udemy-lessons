S01: Get Started with the Course: AI Agents & MCP

L1 Introduction

MCP (Model Context Protocol) is the standard open protocol for connecting AI agents to external tools and services, enabling any agent to use any tool through a universal interface.

The Model Context Protocol (MCP) emerged in late 2024 as the universal standard for connecting AI agents to external tools and services. Before MCP, each agent needed its own custom integration code for every tool it used. MCP eliminates this fragmentation by defining a single protocol that any agent can use to communicate with any tool server.

MCP is already supported by major AI coding assistants (GitHub Copilot, Cursor, Claude Desktop, VS Code) and general-purpose AI applications.

Its adoption was driven by three properties: security (controlled access to tools), scalability (one protocol for unlimited tools), and cross-ecosystem compatibility (works with any MCP-compatible client).

The protocol also supports OAuth 2.1 authentication, enabling remote MCP servers to control who connects and with what privileges.

  • MCP is an open protocol by Anthropic that standardizes how agents discover and invoke external tools
  • All major AI coding assistants and many consumer AI apps already support MCP
  • OAuth 2.1 support enables hosting MCP servers remotely with access control, similar to authenticated APIs
  • MCP works across ecosystems: the same server can serve VS Code, Cursor, Claude Desktop, or any compatible client

L6 What is an Agent?

An agent is an LLM-powered system that controls its own execution flow, reasoning about user requests and deciding which tools to invoke, unlike a simple chatbot that only generates text responses.

An agent differs from a basic chatbot in one critical way: the LLM controls the program's execution flow. In a traditional program, branching logic is hard-coded (if/else).

In a chatbot, the LLM generates a text response.

In an agent, the LLM decides what action to take next, including whether to call a tool, which tool to call, what parameters to pass, and whether the result is sufficient or another action is needed.

The evolution from chatbot to agent happened in stages. ChatGPT launched in November 2022 as a simple interface to an LLM: user sends a message, LLM responds.

The agent evolution added an internal loop between the user's query and the final response.

The LLM now thinks about the query, selects a tool (API call, code execution, file operation, database query), observes the result, and either responds or selects another tool.

This loop continues until the agent determines it has a complete answer. Modern ChatGPT, Copilot, Cursor, and Claude all operate as agents with this architecture.

  • Broad definition: a system where the LLM is responsible for the control flow, making decisions that would otherwise be hard-coded
  • Specific definition: an LLM-powered system that can reason, act, adapt in real time, and use tools
  • The calculator vs. assistant analogy: a calculator executes commands; an assistant plans, decides, then executes
  • The agent loop: receive query -> think (LLM) -> select tool -> execute -> observe result -> think again or respond

L7 ReAct Prompting

ReAct (Reason + Act) is the foundational paradigm where an LLM is prompted to articulate its reasoning before selecting and executing a tool, mimicking human inner monologue during decision-making.

The ReAct paradigm, published in 2022, introduced the idea of making LLMs verbalize their reasoning process before taking action.

It draws from the observation that humans often articulate thoughts internally before acting ('I need milk, it might be in the fridge, I'll go check').

By prompting the LLM to 'think out loud,' it generates a chain of reasoning that leads to a deliberate tool selection.

The original ReAct implementation used a structured prompt format: the LLM outputs a Thought (reasoning), then an Action (tool selection with parameters), then receives an Observation (tool result).

Special stop tokens in the output signaled transitions between phases.

While modern agents no longer use explicit stop tokens (tool calling is now built into LLM APIs), the underlying Thought-Action-Observation loop remains the conceptual backbone of every agent system.

  • ReAct combines Reasoning and Acting: the LLM verbalizes its thinking before selecting a tool
  • The loop is: Thought (why I need this tool) -> Action (call tool with params) -> Observation (interpret result) -> repeat or respond
  • Original implementations used prompt-based stop tokens to signal phase transitions; this was fragile
  • Modern agents internalize this pattern through native tool-calling APIs, making it more reliable

L8 Tool Calling

Modern tool calling embeds available tools as structured metadata in the LLM API call, letting the model return a typed tool-call message instead of relying on prompt-engineered stop tokens.

Modern tool calling replaces the fragile prompt-based approach of ReAct with a native API mechanism.

When making an API call to an LLM (e.g., Anthropic's Claude or OpenAI's GPT), the available tools are passed as structured metadata alongside the user's message.

Each tool definition includes a name, a natural-language description, and an input schema specifying parameter names, types, and constraints.

The LLM processes the user's query in the context of available tools and returns one of two response types: a regular text response (if no tool is needed) or a tool_use message containing the selected tool's name and the arguments to pass.

The agent then executes that tool locally, feeds the result back to the LLM, and the cycle repeats.

This mechanism is more reliable than prompt-based approaches because tool selection is a structured output (not free-text parsing) and the input schema provides type validation.

  • Tools are declared as structured metadata in the API call: name, description, and JSON Schema for parameters
  • The LLM returns a tool_use message type (not free text) when it decides to invoke a tool
  • The agent executes the tool locally, then sends the result back to the LLM for further reasoning
  • Tool descriptions are critical: the LLM reads them to decide which tool matches the user's intent

L12 MCP Overview

MCP solves the N-agents x M-tools integration problem by defining a universal protocol where tools live in separate servers (MCP servers) that any agent (MCP client) can connect to without code duplication.

Before MCP, agents required hard-coded tool implementations. If three agents each needed access to an email service, a database, and a web scraper, that meant nine separate integrations, each potentially implemented differently. This created code duplication, maintenance burden, and no standard way to share tools across agents or teams.

MCP solves this with a client-server architecture.

Tools are packaged into MCP servers, which are standalone programs (similar to microservices) that expose their capabilities through the MCP protocol.

Agents implement an MCP client, which is a standardized interface for discovering and invoking tools from any MCP server.

The result is an M+N integration model instead of M*N: each tool is implemented once in a server, and each agent implements the client protocol once.

An MCP server is conceptually a toolbox. Inside it, each tool is a function (Python, JavaScript, or any language) that accepts parameters and returns data.

The server exposes metadata about each tool (name, description, parameter schema) so that an agent's LLM can decide when and how to use it.

A single MCP client can connect to multiple servers simultaneously, giving the agent access to email, web scraping, database queries, file operations, and more, all through the same protocol.

  • The pre-MCP problem: hard-coded tools per agent led to code duplication, maintenance overhead, and no sharing standard
  • MCP separates tool implementation (servers) from tool consumption (clients), turning M*N integrations into M+N
  • An MCP server is a standalone program exposing tools; think of it as a microservice for agent capabilities
  • A single MCP client can connect to multiple servers simultaneously, aggregating tools from diverse sources
  • Tools are functions with metadata (name, description, parameter schema) that the LLM reads to make selection decisions
  • Anthropic released MCP in November 2024; it became ubiquitous within months due to community adoption

L16 Install MCP Servers

Installing a third-party MCP server involves copying its JSON configuration (command, args, env) into your MCP client's settings file, specifying the transport type, startup command, and any required API keys.

Third-party MCP servers are installed by adding their configuration to the MCP client's settings. The configuration is a JSON object containing three key fields: the command to launch the server (e.g., 'npx' or 'uvx'), the arguments (package name, flags), and environment variables (API keys, tokens).

The Firecrawl web scraping server is used as an example. Its documentation provides a ready-to-copy JSON configuration block.

The transport type (typically STDIO for locally-run servers) is specified, and the server starts automatically when the client launches.

Once connected, the server's tools appear in the client's tool palette, available for the agent to invoke.

Best practice: always use absolute paths for the command binary (e.g., the full path to 'uv' or 'npx') to avoid PATH resolution issues. Include required environment variables (API keys) directly in the configuration rather than relying on shell environment inheritance.

L17 Environment Setup

UV is the recommended Python package manager for MCP development: it handles project initialization, dependency management, virtual environments, and script execution in a single Rust-based tool.

UV (pronounced 'you-vee') is a modern Python package manager written in Rust that consolidates the functionality of pip, virtualenv, poetry, and pyproject.toml management into a single binary. It is significantly faster than alternatives and provides a consistent workflow for MCP server development.

The core UV workflow for MCP projects: (1) 'uv init project-name' creates a new project directory with pyproject.toml, .python-version, and a placeholder entry point.

(2) 'uv venv' creates a virtual environment in the project directory. (3) 'uv add package-name' installs a dependency into the virtual environment and updates the lockfile.

(4) 'uv run script.py' executes a script within the virtual environment without requiring manual activation. (5) 'uv lock' freezes all dependency versions.

(6) 'uv sync' installs all locked dependencies (useful for reproducing environments).

UV's speed advantage comes from Rust-native package resolution and parallel downloads. For MCP development specifically, UV's 'uv run' command is important because MCP server launch commands in client configurations use 'uv run' to execute the server script within the correct virtual environment.

  • UV replaces pip + virtualenv + poetry with a single tool; written in Rust for speed
  • Core commands: init (create project), venv (create environment), add (install package), run (execute script), lock, sync
  • 'uv run' is critical for MCP: client configs use it to launch servers within the correct virtual environment
  • 'uv add' auto-detects the local virtual environment and installs there; no manual activation needed
  • Install UV via curl (Mac/Linux) or PowerShell (Windows); avoid installing via pip

L18 Create a Simple MCP Server

An MCP server is created by importing FastMCP, instantiating it with a name, decorating Python functions with @mcp.tool(), and writing a docstring that serves as the tool description the LLM reads to decide when to invoke it.

The FastMCP high-level interface reduces MCP server creation to three steps. First, import and instantiate: 'from mcp.server.fastmcp import FastMCP; mcp = FastMCP("server-name")'.

Second, define a Python function and decorate it with @mcp.tool().

Third, write a docstring inside the function; this docstring becomes the tool description that the LLM reads to decide whether to invoke the tool.

The function's parameters and their type annotations define the tool's input schema. The function's return value becomes the tool result sent back to the agent. The server is launched by calling 'mcp.run(transport="stdio")' at the bottom of the file, which starts listening for JSON-RPC messages over standard input/output.

The official quickstart documentation at modelcontextprotocol.io provides the canonical reference for server creation. The Python SDK also offers a lower-level interface with more configuration options, but FastMCP is recommended for most use cases because it handles protocol negotiation, message serialization, and tool registration automatically.

  • FastMCP is the high-level Python interface for creating MCP servers with minimal boilerplate
  • The @mcp.tool() decorator registers a function as an MCP tool; the docstring becomes the tool description
  • Function parameters with type annotations automatically define the tool's input schema
  • The tool description (docstring) is what the LLM reads to decide when to use the tool; make it clear and specific
  • mcp.run(transport='stdio') starts the server, listening for JSON-RPC messages on stdin/stdout

L20 Install Your MCP Server

Installing a custom MCP server in a client requires editing the MCP configuration file with the absolute path to the runtime binary, the server script path, and any required environment variables.

After debugging with the MCP Inspector, the server is installed in an MCP client (VS Code, Cursor, etc.) by editing its MCP configuration. In VS Code, this is accessed via Agent Mode > Tools > Add MCP Server, which creates or edits the mcp.json configuration file.

Three common pitfalls during installation: (1) Relative paths fail; always use absolute paths for both the runtime binary (e.g., /home/user/.local/bin/uv) and the server script directory.

Use 'which uv' to find the binary's absolute path.

(2) Environment variables (API keys) must be explicitly included in the config's env field; the server process does not inherit the shell's environment.

(3) The server must be restarted after configuration changes; VS Code provides a restart button in the MCP server panel.

Once configured, the client discovers the server's tools automatically. The number of discovered tools is displayed in the MCP panel, providing immediate verification. The agent can then invoke these tools during conversations, with the user typically confirming tool execution via a 'Continue' button.

  • Restart the server after every configuration change

L23 What is an API?

An API (Application Programming Interface) is a set of URL endpoints that allow one application to request data or services from another programmatically, bypassing the graphical user interface.

An API is a programmatic interface to a service. When a user checks Gmail, they interact through a graphical UI (HTML/CSS). Behind that UI, the frontend makes API calls to a backend server that retrieves and serves data. An API exposes this same data access to external applications, without requiring the graphical interface.

APIs expose their functionality through endpoints: specific URLs that accept HTTP requests and return structured data (typically JSON).

Each endpoint serves a particular function (e.g., '/api/top-headlines' returns recent news, '/api/search' queries by keyword).

Requests include parameters (query strings, headers, body data), and responses include a status code (200 for success, 4xx for client errors, 5xx for server errors) and a data payload.

In the context of MCP, an API is the bridge between an MCP tool and an external service. The MCP tool function makes an HTTP request to the API endpoint, receives the JSON response, and returns it to the agent's LLM. The MCP server is simply another application consuming the API, no different from a web frontend or mobile app.

  • API = Application Programming Interface; the key word is 'interface,' a programmatic way to access a service
  • APIs expose endpoints: specific URLs that accept parameters and return structured data (usually JSON)
  • The request-response cycle: application sends an HTTP request with parameters; API returns a status code and data payload
  • MCP tools are thin wrappers: they translate agent tool calls into API requests and return the response to the LLM
  • Authentication is common: most APIs require an API key or token sent as a query parameter or header

L26 HTTP Methods

HTTP methods define the operation type: GET retrieves data (most common for MCP context augmentation), POST creates/sends data, PUT replaces resources, PATCH partially updates, and DELETE removes resources.

HTTP methods specify the intent of an API request. Five methods cover virtually all API interactions.

GET requests data from the server without modifying anything; this is the most common method for MCP servers because the primary goal is augmenting the agent's context with external data (reading emails, fetching news, querying databases).

POST sends data to the server to create a new resource or trigger an action (sending an email, creating a calendar event). PUT replaces an entire resource with new data.

PATCH partially updates a resource (changing one field without replacing the whole object). DELETE removes a resource.

For MCP servers specifically, GET dominates because MCP's core value proposition is Model Context Protocol; the goal is enriching the LLM's context with real-time data.

However, action-oriented MCP tools (send email, create file, place an order) use POST, PUT, PATCH, or DELETE depending on the operation.

The HTTP method is an implementation detail of the MCP tool; the agent and protocol do not care which method the tool uses internally.

  • GET: read data without side effects; most common for MCP context augmentation
  • POST: create a new resource or send data (send email, create event, upload file)
  • PUT: replace an entire resource with new data
  • PATCH: partially update a resource (change one field)
  • DELETE: remove a resource
  • MCP tools are GET-heavy because MCP is about augmenting context; but action tools use POST/PUT/DELETE

L27 Notebook: Experiment with an API

Making API calls in Python uses the 'requests' library: construct the URL with endpoint and query parameters, send a GET request, check the status code, and parse the JSON response.

Python's requests library is the standard tool for making HTTP API calls and forms the backbone of most MCP tool implementations. The workflow mirrors manual API testing: construct the URL (base URL + endpoint + query parameters), send the request, check the response status code, and parse the JSON payload.

Query parameters are built as a Python dictionary and converted to URL-encoded format using urllib.parse.urlencode(). The full URL is assembled as an f-string: '{base_url}/{endpoint}?{encoded_params}'. The request is sent with requests.get(url), and the response is checked: status code 200 indicates success, after which response.json() parses the payload into a Python dictionary.

This exact pattern (build params dict, encode URL, make request, check status, parse JSON) becomes the core of most MCP tool functions. The function accepts agent-provided parameters, constructs the API call, and returns the parsed response to the LLM. API keys should be stored in environment variables in production, never hard-coded.

L41 JSON-RPC Messages

MCP uses JSON-RPC 2.0 as its message format: the client sends a request with method name, parameters, and an ID; the server returns a response with the result and the same ID for correlation.

JSON-RPC (JSON Remote Procedure Call) is the message format used for all communication between MCP clients and servers. It is a lightweight, human-readable standard for encoding function calls and their results as JSON objects.

A client request contains four fields: 'jsonrpc' (protocol version, always '2.0'), 'method' (the tool/function name to call), 'params' (the arguments as a JSON object), and 'id' (a unique identifier for correlating requests with responses).

A server response contains three fields: 'jsonrpc' (version), 'result' (the function's return value), and 'id' (matching the request's ID).

JSON-RPC was chosen for MCP because it is human-readable (useful for debugging and for LLMs that process text), language-agnostic (works with any programming language), lightweight (minimal overhead), and well-established (a mature standard with broad tooling support). It is conceptually similar to gRPC but uses JSON instead of Protocol Buffers, trading some performance for readability.

  • Response fields: jsonrpc (version), result (return value), id (matches the request)
  • Human-readable format benefits debugging and LLM processing
  • Similar to gRPC but uses JSON instead of Protocol Buffers for readability over raw performance

L42 Transports in MCP

STDIO transport runs the MCP server as a local process communicating via stdin/stdout (launched by command), while Streamable HTTP exposes the server at a URL endpoint, enabling remote access from any machine over the network.

The transport determines how JSON-RPC messages physically travel between client and server. STDIO (Standard Input/Output) runs the MCP server as a child process of the client.

The client launches the server using a command (e.g., 'uv run main.py'), and communication happens through the process's stdin (client-to-server) and stdout (server-to-client).

This is fast and secure (no network exposure) but requires both client and server on the same machine.

Streamable HTTP runs the MCP server as an HTTP service accessible via a URL endpoint.

The client sends JSON-RPC requests as HTTP POST requests to the server's endpoint, and the server returns JSON-RPC responses.

This enables remote deployment: the server can be hosted on a cloud provider, and any client with the URL can connect.

Streamable HTTP replaced SSE (Server-Sent Events) from the 2024 MCP specification because SSE only supported server-to-client streaming, while Streamable HTTP supports bidirectional communication.

The choice of transport does not affect tool implementation. The same @mcp.tool() decorated functions work identically on both transports. The transport is configured at server startup: mcp.run(transport='stdio') for local or mcp.run(transport='http') for remote. Client configuration differs: STDIO configs specify a launch command, while HTTP configs specify a URL.

  • STDIO: server runs as a local child process; communication via stdin/stdout; no network exposure
  • Streamable HTTP: server runs as an HTTP service at a URL; accessible from any machine over the network
  • SSE (Server-Sent Events) is deprecated; it only supported server-to-client streaming
  • Transport choice does not affect tool code; same @mcp.tool() functions work on both
  • STDIO config uses a launch command; HTTP config uses a URL endpoint
  • STDIO is for development and personal use; Streamable HTTP is for production and shared deployment

L45 Malicious MCP Servers

A malicious MCP server exploits the agent's inability to see implementation code by hiding arbitrary operations (data exfiltration, file manipulation, shell commands) inside an otherwise legitimate-looking tool function.

When an MCP client sends a tool list to its language model, each tool is represented solely by its name, a natural-language description, and a JSON schema of accepted parameters.

No source code is transmitted. The LLM decides whether to invoke a tool based entirely on this metadata, and the user typically approves based on the same limited information.

This architecture creates a critical blind spot: the actual function body can contain any code, including subprocess calls, file system operations, network requests, or data exfiltration routines, all invisible to both the agent and the user.

The threat is most severe under the stdio transport, where the MCP server process runs on the user's own machine with the same OS-level permissions as any local program.

Code executed via stdio can read and write files, access environment variables (including API keys and credentials), and make outbound network connections.

A tool that appears to "get weather data" or "multiply two numbers" can simultaneously run shell commands, create log files containing stolen data, or delete critical files.

The user sees only the tool's return value, which can be perfectly correct, while the side effects remain completely hidden.

  • Tool calls sent to the LLM contain only metadata (name, description, parameter schema), never implementation code.
  • A malicious tool can perform harmful side effects (shell commands, file writes, data exfiltration) while returning a correct, expected result.
  • Stdio transport is the highest-risk vector because the server code runs locally with the user's full OS permissions.
  • Installing an unvetted MCP server is equivalent to downloading and executing an unsigned binary from the internet.
  • Input data sent to a tool can be leaked by the malicious implementation to external servers or local log files.

L46 Create a Malicious MCP Server

L49 Streamable HTTP

Streamable HTTP is the transport protocol that enables MCP servers to operate remotely over standard HTTP connections, replacing the local-only stdio model with a scalable, stateless, cloud-ready architecture.

Since MCP's initial release, most publicly available servers ran locally via the stdio transport: the agent and server lived on the same machine, communicating through standard input/output streams.

While functional for developers, this model does not scale to non-technical users, multi-user environments, or cloud-native architectures.

Streamable HTTP solves this by allowing MCP servers to be accessed over standard HTTP endpoints, just like any web API.

In the stdio model, the full workflow (user query, agent reasoning, tool invocation, response) happens entirely within a single machine.

With Streamable HTTP, the MCP server can live on a separate machine or in the cloud.

The agent sends HTTP requests to the server's URL, the server executes the tool logic on its own infrastructure, and returns results over the same HTTP connection.

This architecture is stateless, horizontally scalable, and compatible with existing web infrastructure (load balancers, reverse proxies, CDNs).

It also enables centralized hosting: the team that builds a service can now expose it as an MCP server alongside their existing API and UI, maintaining full control over execution, security, and updates.

  • Stdio transport requires the server process to run on the same machine as the agent; Streamable HTTP removes this constraint.
  • Streamable HTTP turns an MCP server into a standard HTTP service, compatible with existing web infrastructure.
  • The architecture is stateless and horizontally scalable, supporting multiple concurrent agent connections.
  • Service teams can host MCP servers centrally alongside their existing API and UI interfaces.
  • The endpoint convention is typically /mcp appended to the server's base URL (e.g., http://localhost:10000/mcp).
  • Remote servers shift code execution from the user's machine to the server operator's infrastructure, improving security.

L57 Why not Local Auth in MCP?

Local MCP authentication via API keys in configuration files is inadequate for mainstream adoption because it requires technical expertise, runs untrusted code on the user's machine, and cannot scale to non-technical users.

The local authentication model for stdio-based MCP servers relies on users manually obtaining API keys from developer dashboards and pasting them into JSON configuration files. While this works for software engineers who are comfortable navigating developer portals, it presents insurmountable barriers for non-technical users. The problems with local auth extend beyond usability.

First, installation complexity: users must follow tutorials to install MCP servers, configure runtime environments (UV, Python, Node), and manage configuration files.

Second, security risk: stdio servers run on the user's machine with full OS permissions, and as demonstrated in the security module, the user cannot verify what the server code actually does.

Third, scalability: there is no centralized management of access, permissions, or revocation. If an API key is compromised, there is no automated way to rotate it across all clients.

Fourth, user experience: expecting non-technical users to copy API keys and edit JSON files is fundamentally incompatible with mainstream software distribution.

These limitations make local auth suitable only for developer tooling and personal automation, not for the widespread agent ecosystem that MCP aims to enable.

  • Local auth requires users to obtain API keys from developer dashboards and paste them into JSON configuration files.

  • There is no centralized mechanism for access management, permission scoping, or credential revocation.

L59 What is OAuth

OAuth 2.1 is a delegated authorization protocol where the MCP client follows a multi-step 'breadcrumb trail' of well-known endpoints to discover the authorization server, register itself, authenticate the user, obtain scoped tokens, and present them to the MCP server for validated access.

OAuth 2.1 is the officially mandated authentication standard for MCP. At a high level, it is a protocol that allows a client (the MCP agent) to obtain limited, scoped access to a server's resources on behalf of a user, without the user sharing credentials directly with the client.

The flow begins when the MCP client attempts to connect to the MCP server and receives a 401 Unauthorized response.

This response includes a header pointing to a well-known metadata endpoint (e.g., /.well-known/oauth-protected-resource).

The client follows this URL to discover the authorization server's location, supported methods, and available scopes.

It then follows another breadcrumb to the authorization server's own well-known configuration (/.well-known/openid-configuration), which provides endpoints for client registration, authorization, and token exchange.

The client dynamically registers itself with the authorization server, receiving a client_id.

It then redirects the user to the authorization server's login page, where the user authenticates (via username/password, Google login, etc.) and consents to the requested scopes (e.g., 'search:read').

Upon successful authentication, the authorization server issues an authorization code, which the client exchanges for an access token (JWT).

The client stores this token and includes it as a Bearer token in subsequent requests to the MCP server.

The MCP server validates the token's signature, issuer, audience, and scopes before allowing the tool call to proceed.

  • OAuth 2.1 enables delegated authorization: the user authenticates once, and the client receives a scoped token to act on their behalf.
  • The flow starts with a 401 response containing a pointer to the well-known metadata endpoint.
  • The client follows a breadcrumb trail: resource metadata, then authorization server configuration, then registration, then login.
  • Dynamic client registration allows any compliant MCP client to register with any compliant server without pre-configuration.
  • Scopes (e.g., 'search:read') define what operations the token authorizes, enabling fine-grained access control.
  • The final access token is a JWT (JSON Web Token) containing the issuer, audience, scopes, and a cryptographic signature.

L60 OAuth 2.1 Workflow

Walking through the OAuth 2.1 flow manually (as if impersonating the MCP client) reveals the exact sequence of HTTP calls, redirects, and token exchanges that happen automatically when a compliant client authenticates with a protected MCP server.

To demystify OAuth 2.1, it is instructive to manually execute each step that an MCP client performs automatically. Starting with the MCP Inspector connected to a protected server, the first tool call returns a 401 Unauthorized response. The response headers contain a resource metadata URI pointing to /.well-known/oauth-protected-resource on the MCP server.

Calling this endpoint returns a JSON document containing the authorization server's URL, the supported authentication method (Bearer), the resource identifier, and the available scopes (e.g., 'search:read').

The client then follows the authorization server URL to its /.well-known/openid-configuration, which provides the registration endpoint, authorization endpoint, and token endpoint.

The client registers itself at the registration endpoint, receiving a client_id.

It then constructs an authorization URL with parameters including response_type=code, the client_id, a redirect_uri, the requested scope, and a state parameter for CSRF protection.

Opening this URL in a browser presents the user with a login page. After authentication (e.g., via Google), the user is redirected back with an authorization code.

The client exchanges this code at the token endpoint for a JWT access token. This token is then included as a Bearer header in subsequent MCP requests, which the server validates.

The entire process, while complex when traced manually, happens transparently and in seconds when performed by a compliant MCP client.

  • The 401 response header contains the breadcrumb to /.well-known/oauth-protected-resource on the MCP server itself.
  • The resource metadata JSON provides the authorization server URL, supported methods, and available scopes.
  • The authorization server's openid-configuration exposes registration, authorization, and token endpoints.
  • Client registration is dynamic: the client sends its redirect_uri and receives a client_id without human intervention.
  • The authorization URL includes response_type=code, client_id, redirect_uri, scope, and a state parameter for CSRF protection.
  • The complete flow, though multi-step, executes transparently in seconds when handled by a compliant client.

L65 Token Validation

Token validation verifies the JWT's cryptographic signature, issuer, audience, and required scopes using the ScaleKit SDK, with scope checking applied only to tool call requests to allow unauthenticated session initialization.

After the middleware confirms that a Bearer token is present, the next step is validating that the token is legitimate, unmodified, and authorized for the requested operation. JSON Web Tokens (JWTs) contain three parts: a header (algorithm and type), a payload (issuer, audience, scopes, expiration, and other claims), and a cryptographic signature. Validation must verify all three.

The ScaleKit SDK simplifies this to a single method call: `validate_token(token, validation_options)`.

The validation options specify the expected issuer (the ScaleKit environment URL), the expected audience (the MCP server's resource name, including the trailing slash), and optionally the required scopes.

The SDK verifies the JWT signature against ScaleKit's public keys, checks that the issuer and audience match, validates the expiration, and confirms that the token contains the required scopes.

An important nuance is that scope validation should only be applied to tool call requests, not to all MCP requests.

MCP clients may connect to the server for session initialization or capability discovery before making tool calls.

To distinguish tool calls, the middleware parses the request body and checks if the JSON-RPC method field indicates a tool invocation.

If it is a tool call, the required scope (e.g., 'search:read') is added to the validation options. If it is a non-tool request, validation proceeds without scope checking.

If `validate_token` succeeds, the request passes through to the MCP handler.

If it raises an exception (invalid signature, wrong issuer, missing scope, expired token), the middleware catches it and returns a 401 error.

L69 What is RAG?

RAG (Retrieval-Augmented Generation) overcomes an LLM's knowledge cutoff by extracting text from documents, indexing it in a vector database, retrieving relevant chunks at query time, and injecting them as context for the model to generate grounded answers.

Large language models are trained on static datasets and therefore cannot natively discuss real-time events, proprietary company data, or any information absent from their training corpus. Retrieval-Augmented Generation addresses this by introducing an external knowledge pipeline with three distinct phases.

The first phase, ETL (Extract, Transform, Load), takes unstructured documents (PDFs, Word files, HTML pages) and processes them into a searchable format inside a vector database.

The second phase, Retrieval, takes a user's natural-language query, converts it into the same vector space, and finds the most semantically similar document chunks.

The third phase, Generation, feeds those retrieved chunks as context into the LLM's prompt, allowing it to produce answers grounded in the retrieved material rather than relying solely on parametric memory.

  • LLMs cannot discuss topics outside their training data; RAG fills this gap with external retrieval.
  • ETL (Extract, Transform, Load) converts unstructured documents into indexed, searchable vector representations.
  • Retrieval uses semantic similarity (not keyword matching) to find the most relevant document chunks for a given query.
  • Generation injects retrieved chunks into the LLM context window so the model can produce grounded, accurate answers.
  • RAG works with any unstructured data source: PDFs, HTML, Word documents, plain text files.

L70 RAG Pipeline

The RAG pipeline transforms unstructured documents through a sequence of extract, chunk, embed, store, retrieve, and generate steps, where chunking controls granularity and embeddings enable semantic search instead of keyword matching.

A detailed RAG pipeline expands the three high-level phases (ETL, Retrieval, Generation) into concrete processing steps.

During extraction, raw text is pulled from unstructured files using parsing tools (LlamaIndex, LangChain, etc.).

That raw text must then be split into chunks because entire documents are too large to fit into a single LLM context window and because smaller, focused passages yield more precise retrieval results.

Each chunk is converted into a numerical embedding vector that captures its semantic meaning. These vectors are stored in a vector database that indexes them for fast similarity search.

At query time, the user's question is also embedded into the same vector space. The vector database returns the top-k most similar chunks.

These chunks, along with the original question, are assembled into a prompt and sent to the LLM, which generates an answer grounded in the retrieved context.

The quality of the final answer depends heavily on two earlier decisions: chunk size (too large loses precision; too small loses context) and embedding model quality (determines how well meaning is captured in the vector space).

  • Extraction pulls raw text from PDFs, HTML, Word files, and other unstructured sources using parsing libraries.
  • Chunking splits extracted text into smaller passages; chunk size is a critical design decision affecting retrieval precision.
  • Each chunk is embedded into a high-dimensional vector that captures its semantic meaning.
  • Vectors are stored in a vector database optimized for nearest-neighbor similarity search.
  • At query time, the user's question is embedded into the same space and matched against stored chunk vectors.
  • Retrieved chunks are injected into the LLM prompt as context for answer generation.

L71 Embeddings

Embeddings are high-dimensional numerical vectors that capture semantic meaning, allowing text similarity to be measured by geometric distance rather than keyword overlap.

An embedding is a mapping from human-readable data (text, images, audio) into a point in a high-dimensional numerical space, where each dimension captures some facet of meaning.

Conceptually, two dimensions might represent 'positivity' and 'topic relevance,' but real embedding models use thousands of dimensions (OpenAI's text-embedding-3-small uses 1,536 dimensions) to capture nuanced semantic relationships.

The power of embeddings lies in the geometric property that semantically similar content maps to nearby points.

'The cat sat on the mat' and 'A feline rested on the rug' would have vectors close together in embedding space despite sharing zero keywords.

This is what enables semantic search: instead of matching exact words, the system measures vector distance (typically cosine similarity) to find the most relevant content.

Embedding models are distinct from generative LLMs; they are specialized neural networks trained specifically to produce meaningful vector representations, not to generate text.

  • Embeddings map text into high-dimensional numerical vectors where each dimension captures a facet of meaning.
  • Semantic similarity becomes geometric proximity: similar texts have nearby vectors regardless of shared keywords.
  • Real embedding models use thousands of dimensions (e.g., text-embedding-3-small has 1,536 dimensions).
  • Embedding models are separate from generative LLMs; they are specialized for representation, not text generation.
  • Distance metrics like cosine similarity quantify how related two pieces of text are in embedding space.

L72 Vector Databases

Vector databases are specialized storage systems optimized for indexing and searching embedding vectors by similarity, enabling semantic search, recommendation systems, and RAG-based question answering at scale.

After embedding text chunks into numerical vectors, those vectors need a storage system that can efficiently perform nearest-neighbor searches across potentially millions of entries.

A regular database could store vectors as arrays, but it lacks the indexing structures needed for fast similarity search.

Vector databases solve this by organizing vectors using specialized index structures (HNSW, IVF, etc.) that allow sub-linear search times.

The query workflow is straightforward: a user's question is embedded into the same vector space, and the database returns the k vectors closest to it (by cosine similarity, Euclidean distance, or dot product).

Each returned vector is linked back to its original text chunk and metadata, providing the retrieval step of RAG.

Popular vector databases include ChromaDB (lightweight, local-first, open source), Pinecone (managed cloud service), Weaviate, Qdrant, and Milvus.

ChromaDB is particularly well-suited for prototyping and small-to-medium workloads because it requires no server setup and includes a built-in default embedding model.

  • Vector databases use specialized index structures (HNSW, IVF) for efficient nearest-neighbor search over embeddings.
  • Queries work by embedding the question and finding the k closest stored vectors by distance metric.

  • ChromaDB is open source, runs locally, and includes a default embedding model, making it ideal for prototyping.
  • Vector databases power three key use cases: semantic search, recommendation systems, and RAG-based Q&A.

L73 Agentic RAG

Agentic RAG replaces the static query-to-database pipeline with an LLM agent that autonomously decides when to query the vector database, how to refine its searches, and whether additional retrieval rounds are needed before generating a final answer.

Standard RAG pipelines are linear: a user query goes directly to the vector database, retrieved chunks go directly to the LLM, and a response is generated in a single pass. This works for simple questions but breaks down when the query is ambiguous, requires multi-step reasoning, or needs information from multiple document sections.

Agentic RAG inserts an LLM agent between the user and the retrieval system.

The ETL phase remains identical (extract, chunk, embed, store), but the retrieval and generation phases are now orchestrated by an agent that follows a tool-use loop.

The agent receives the user's question, decides whether it needs external knowledge, formulates an optimized query for the vector database (which may differ from the user's original phrasing), evaluates the returned chunks, and may issue additional queries if the first results are insufficient.

This reasoning loop continues until the agent has enough context to produce a complete answer.

In MCP terms, the vector database query becomes a tool exposed by an MCP server, and the agent invokes it through the standard MCP tool-calling protocol.

  • Standard RAG is a single-pass pipeline; Agentic RAG adds a reasoning loop around retrieval.
  • The agent autonomously decides when, what, and how many times to query the vector database.
  • The agent can reformulate the user's question into more effective search queries.
  • Multiple retrieval rounds allow the agent to gather context from different document sections before answering.
  • The vector database query function becomes an MCP tool, integrating RAG into the standard MCP architecture.

Deploying to Render involves creating a Web Service, connecting the GitHub repository, setting the build command to 'uv sync' and the start command to 'uvicorn main:app', configuring environment variables, and specifying host 0.0.0.0 with port 10000.

The Render deployment process connects the GitHub repository to a new Web Service. After signing in and granting Render access to the specific GitHub repository, the configuration requires four key settings.

First, the build command is set to 'uv sync' (instead of the default 'pip install -r requirements.txt'), which installs all dependencies from the committed uv.lock file.

Third, environment variables from the local .env file are added through Render's dashboard (Settings > Environment). Fourth, the runtime is set to Python with the correct branch (master/main).

Once deployed, Render provides a public URL (e.g., demo-gnews-remote-mcp.onrender.com) that serves as the MCP server's permanent address.
