Lesson 1: Introduction

MCP (Model Context Protocol) is the standard open protocol for connecting AI agents to external tools and services, enabling any agent to use any tool through a universal interface.

Core Concept

The Model Context Protocol (MCP) emerged in late 2024 as the universal standard for connecting AI agents to external tools and services. Before MCP, each agent needed its own custom integration code for every tool it used. MCP eliminates this fragmentation by defining a single protocol that any agent can use to communicate with any tool server. MCP is already supported by major AI coding assistants (GitHub Copilot, Cursor, Claude Desktop, VS Code) and general-purpose AI applications. Its adoption was driven by three properties: security (controlled access to tools), scalability (one protocol for unlimited tools), and cross-ecosystem compatibility (works with any MCP-compatible client). The protocol also supports OAuth 2.1 authentication, enabling remote MCP servers to control who connects and with what privileges.

Key Points

  • MCP is an open protocol by Anthropic that standardizes how agents discover and invoke external tools
  • All major AI coding assistants and many consumer AI apps already support MCP
  • OAuth 2.1 support enables hosting MCP servers remotely with access control, similar to authenticated APIs
  • MCP works across ecosystems: the same server can serve VS Code, Cursor, Claude Desktop, or any compatible client

Lesson 6: What is an Agent?

An agent is an LLM-powered system that controls its own execution flow, reasoning about user requests and deciding which tools to invoke, unlike a simple chatbot that only generates text responses.

Core Concept

An agent differs from a basic chatbot in one critical way: the LLM controls the program's execution flow. In a traditional program, branching logic is hard-coded (if/else). In a chatbot, the LLM generates a text response. In an agent, the LLM decides what action to take next, including whether to call a tool, which tool to call, what parameters to pass, and whether the result is sufficient or another action is needed. The evolution from chatbot to agent happened in stages. ChatGPT launched in November 2022 as a simple interface to an LLM: user sends a message, LLM responds. The agent evolution added an internal loop between the user's query and the final response. The LLM now thinks about the query, selects a tool (API call, code execution, file operation, database query), observes the result, and either responds or selects another tool. This loop continues until the agent determines it has a complete answer. Modern ChatGPT, Copilot, Cursor, and Claude all operate as agents with this architecture.

Key Points

  • Broad definition: a system where the LLM is responsible for the control flow, making decisions that would otherwise be hard-coded
  • Specific definition: an LLM-powered system that can reason, act, adapt in real time, and use tools
  • The calculator vs. assistant analogy: a calculator executes commands; an assistant plans, decides, then executes
  • The agent loop: receive query -> think (LLM) -> select tool -> execute -> observe result -> think again or respond

Lesson 7: ReAct Prompting

ReAct (Reason + Act) is the foundational paradigm where an LLM is prompted to articulate its reasoning before selecting and executing a tool, mimicking human inner monologue during decision-making.

Core Concept

The ReAct paradigm, published in 2022, introduced the idea of making LLMs verbalize their reasoning process before taking action. It draws from the observation that humans often articulate thoughts internally before acting ('I need milk, it might be in the fridge, I'll go check'). By prompting the LLM to 'think out loud,' it generates a chain of reasoning that leads to a deliberate tool selection. The original ReAct implementation used a structured prompt format: the LLM outputs a Thought (reasoning), then an Action (tool selection with parameters), then receives an Observation (tool result). Special stop tokens in the output signaled transitions between phases. While modern agents no longer use explicit stop tokens (tool calling is now built into LLM APIs), the underlying Thought-Action-Observation loop remains the conceptual backbone of every agent system.

Key Points

  • ReAct combines Reasoning and Acting: the LLM verbalizes its thinking before selecting a tool
  • The loop is: Thought (why I need this tool) -> Action (call tool with params) -> Observation (interpret result) -> repeat or respond
  • Original implementations used prompt-based stop tokens to signal phase transitions; this was fragile
  • Modern agents internalize this pattern through native tool-calling APIs, making it more reliable

Lesson 8: Tool Calling

Modern tool calling embeds available tools as structured metadata in the LLM API call, letting the model return a typed tool-call message instead of relying on prompt-engineered stop tokens.

Core Concept

Modern tool calling replaces the fragile prompt-based approach of ReAct with a native API mechanism. When making an API call to an LLM (e.g., Anthropic's Claude or OpenAI's GPT), the available tools are passed as structured metadata alongside the user's message. Each tool definition includes a name, a natural-language description, and an input schema specifying parameter names, types, and constraints. The LLM processes the user's query in the context of available tools and returns one of two response types: a regular text response (if no tool is needed) or a tool_use message containing the selected tool's name and the arguments to pass. The agent then executes that tool locally, feeds the result back to the LLM, and the cycle repeats. This mechanism is more reliable than prompt-based approaches because tool selection is a structured output (not free-text parsing) and the input schema provides type validation.

Key Points

  • Tools are declared as structured metadata in the API call: name, description, and JSON Schema for parameters
  • The LLM returns a tool_use message type (not free text) when it decides to invoke a tool
  • The agent executes the tool locally, then sends the result back to the LLM for further reasoning
  • Tool descriptions are critical: the LLM reads them to decide which tool matches the user's intent

Lesson 12: MCP Overview

MCP solves the N-agents x M-tools integration problem by defining a universal protocol where tools live in separate servers (MCP servers) that any agent (MCP client) can connect to without code duplication.

Core Concept

Before MCP, agents required hard-coded tool implementations. If three agents each needed access to an email service, a database, and a web scraper, that meant nine separate integrations, each potentially implemented differently. This created code duplication, maintenance burden, and no standard way to share tools across agents or teams. MCP solves this with a client-server architecture. Tools are packaged into MCP servers, which are standalone programs (similar to microservices) that expose their capabilities through the MCP protocol. Agents implement an MCP client, which is a standardized interface for discovering and invoking tools from any MCP server. The result is an M+N integration model instead of M*N: each tool is implemented once in a server, and each agent implements the client protocol once. An MCP server is conceptually a toolbox. Inside it, each tool is a function (Python, JavaScript, or any language) that accepts parameters and returns data. The server exposes metadata about each tool (name, description, parameter schema) so that an agent's LLM can decide when and how to use it. A single MCP client can connect to multiple servers simultaneously, giving the agent access to email, web scraping, database queries, file operations, and more, all through the same protocol.

Key Points

  • The pre-MCP problem: hard-coded tools per agent led to code duplication, maintenance overhead, and no sharing standard
  • MCP separates tool implementation (servers) from tool consumption (clients), turning M*N integrations into M+N
  • An MCP server is a standalone program exposing tools; think of it as a microservice for agent capabilities
  • A single MCP client can connect to multiple servers simultaneously, aggregating tools from diverse sources
  • Tools are functions with metadata (name, description, parameter schema) that the LLM reads to make selection decisions
  • Anthropic released MCP in November 2024; it became ubiquitous within months due to community adoption

Lesson 16: Install MCP Servers

Installing a third-party MCP server involves copying its JSON configuration (command, args, env) into your MCP client's settings file, specifying the transport type, startup command, and any required API keys.

Core Concept

Third-party MCP servers are installed by adding their configuration to the MCP client's settings. The configuration is a JSON object containing three key fields: the command to launch the server (e.g., 'npx' or 'uvx'), the arguments (package name, flags), and environment variables (API keys, tokens). The Firecrawl web scraping server is used as an example. Its documentation provides a ready-to-copy JSON configuration block. In VS Code, this configuration is added via Settings > MCP > Add MCP Server (or by editing the mcp.json file directly). The transport type (typically STDIO for locally-run servers) is specified, and the server starts automatically when the client launches. Once connected, the server's tools appear in the client's tool palette, available for the agent to invoke. Best practice: always use absolute paths for the command binary (e.g., the full path to 'uv' or 'npx') to avoid PATH resolution issues. Include required environment variables (API keys) directly in the configuration rather than relying on shell environment inheritance.

Key Points

  • MCP server configs are JSON objects with three fields: command, args, and env (environment variables)
  • Most third-party servers provide a ready-to-copy config block in their documentation
  • In VS Code: Settings > MCP > Add MCP Server, or edit mcp.json directly
  • Use absolute paths for the command binary to avoid PATH resolution failures
  • API keys go in the env field of the config; do not rely on shell environment inheritance

Lesson 23: What is an API?

An API (Application Programming Interface) is a set of URL endpoints that allow one application to request data or services from another programmatically, bypassing the graphical user interface.

Core Concept

An API is a programmatic interface to a service. When a user checks Gmail, they interact through a graphical UI (HTML/CSS). Behind that UI, the frontend makes API calls to a backend server that retrieves and serves data. An API exposes this same data access to external applications, without requiring the graphical interface. APIs expose their functionality through endpoints: specific URLs that accept HTTP requests and return structured data (typically JSON). Each endpoint serves a particular function (e.g., '/api/top-headlines' returns recent news, '/api/search' queries by keyword). Requests include parameters (query strings, headers, body data), and responses include a status code (200 for success, 4xx for client errors, 5xx for server errors) and a data payload. In the context of MCP, an API is the bridge between an MCP tool and an external service. The MCP tool function makes an HTTP request to the API endpoint, receives the JSON response, and returns it to the agent's LLM. The MCP server is simply another application consuming the API, no different from a web frontend or mobile app.

Key Points

  • API = Application Programming Interface; the key word is 'interface,' a programmatic way to access a service
  • APIs expose endpoints: specific URLs that accept parameters and return structured data (usually JSON)
  • The request-response cycle: application sends an HTTP request with parameters; API returns a status code and data payload
  • MCP tools are thin wrappers: they translate agent tool calls into API requests and return the response to the LLM
  • Authentication is common: most APIs require an API key or token sent as a query parameter or header

Lesson 26: HTTP Methods

HTTP methods define the operation type: GET retrieves data (most common for MCP context augmentation), POST creates/sends data, PUT replaces resources, PATCH partially updates, and DELETE removes resources.

Core Concept

HTTP methods specify the intent of an API request. Five methods cover virtually all API interactions. GET requests data from the server without modifying anything; this is the most common method for MCP servers because the primary goal is augmenting the agent's context with external data (reading emails, fetching news, querying databases). POST sends data to the server to create a new resource or trigger an action (sending an email, creating a calendar event). PUT replaces an entire resource with new data. PATCH partially updates a resource (changing one field without replacing the whole object). DELETE removes a resource. For MCP servers specifically, GET dominates because MCP's core value proposition is Model Context Protocol; the goal is enriching the LLM's context with real-time data. However, action-oriented MCP tools (send email, create file, place an order) use POST, PUT, PATCH, or DELETE depending on the operation. The HTTP method is an implementation detail of the MCP tool; the agent and protocol do not care which method the tool uses internally.

Key Points

  • GET: read data without side effects; most common for MCP context augmentation
  • POST: create a new resource or send data (send email, create event, upload file)
  • PUT: replace an entire resource with new data
  • PATCH: partially update a resource (change one field)
  • DELETE: remove a resource
  • MCP tools are GET-heavy because MCP is about augmenting context; but action tools use POST/PUT/DELETE

Core Concept

Lesson 40: Client-Server Architecture

MCP separates the agent (client) from the toolkits (servers) into a client-server architecture where the client sends tool-call requests and the server executes them, even though both may run on the same machine.

Core Concept

The MCP client-server architecture separates tool consumption from tool execution. The MCP client lives within the agent: it receives the LLM's tool selection, formats it as a JSON-RPC request, sends it to the MCP server, receives the result, and feeds it back to the LLM. The MCP server is a separate process that receives tool-call requests, executes the corresponding functions, and returns results. This separation exists even when both run on the same machine (STDIO transport). The server is a distinct process from the client, similar to how a localhost web server is separate from the browser accessing it. This architectural separation enables the key MCP benefits: tool reuse across agents, independent server deployment and versioning, and the ability to move servers to remote machines without changing agent code. An important distinction: the MCP client-server architecture operates entirely in the backend. If the agent has a frontend (web UI, voice interface), that frontend-backend relationship is a separate client-server model. The MCP client might simultaneously be the backend server for a web frontend, while also being the client of multiple MCP servers. These are different layers of the architecture.

  • The MCP server is a separate process that executes tool functions and returns results

Lesson 41: JSON-RPC Messages

MCP uses JSON-RPC 2.0 as its message format: the client sends a request with method name, parameters, and an ID; the server returns a response with the result and the same ID for correlation.

Core Concept

JSON-RPC (JSON Remote Procedure Call) is the message format used for all communication between MCP clients and servers. It is a lightweight, human-readable standard for encoding function calls and their results as JSON objects. A client request contains four fields: 'jsonrpc' (protocol version, always '2.0'), 'method' (the tool/function name to call), 'params' (the arguments as a JSON object), and 'id' (a unique identifier for correlating requests with responses). A server response contains three fields: 'jsonrpc' (version), 'result' (the function's return value), and 'id' (matching the request's ID). JSON-RPC was chosen for MCP because it is human-readable (useful for debugging and for LLMs that process text), language-agnostic (works with any programming language), lightweight (minimal overhead), and well-established (a mature standard with broad tooling support). It is conceptually similar to gRPC but uses JSON instead of Protocol Buffers, trading some performance for readability.

Key Points

  • Request fields: jsonrpc (version), method (function name), params (arguments), id (correlation ID)
  • Response fields: jsonrpc (version), result (return value), id (matches the request)
  • Human-readable format benefits debugging and LLM processing
  • Similar to gRPC but uses JSON instead of Protocol Buffers for readability over raw performance

Lesson 42: Transports in MCP

STDIO transport runs the MCP server as a local process communicating via stdin/stdout (launched by command), while Streamable HTTP exposes the server at a URL endpoint, enabling remote access from any machine over the network.

Core Concept

The transport determines how JSON-RPC messages physically travel between client and server. STDIO (Standard Input/Output) runs the MCP server as a child process of the client. The client launches the server using a command (e.g., 'uv run main.py'), and communication happens through the process's stdin (client-to-server) and stdout (server-to-client). This is fast and secure (no network exposure) but requires both client and server on the same machine. Streamable HTTP runs the MCP server as an HTTP service accessible via a URL endpoint. The client sends JSON-RPC requests as HTTP POST requests to the server's endpoint, and the server returns JSON-RPC responses. This enables remote deployment: the server can be hosted on a cloud provider, and any client with the URL can connect. Streamable HTTP replaced SSE (Server-Sent Events) from the 2024 MCP specification because SSE only supported server-to-client streaming, while Streamable HTTP supports bidirectional communication. The choice of transport does not affect tool implementation. The same @mcp.tool() decorated functions work identically on both transports. The transport is configured at server startup: mcp.run(transport='stdio') for local or mcp.run(transport='http') for remote. Client configuration differs: STDIO configs specify a launch command, while HTTP configs specify a URL.

Key Points

  • STDIO: server runs as a local child process; communication via stdin/stdout; no network exposure
  • Streamable HTTP: server runs as an HTTP service at a URL; accessible from any machine over the network
  • SSE (Server-Sent Events) is deprecated; it only supported server-to-client streaming
  • Transport choice does not affect tool code; same @mcp.tool() functions work on both
  • STDIO config uses a launch command; HTTP config uses a URL endpoint
  • STDIO is for development and personal use; Streamable HTTP is for production and shared deployment

Lesson 45: Malicious MCP Servers

A malicious MCP server exploits the agent's inability to see implementation code by hiding arbitrary operations (data exfiltration, file manipulation, shell commands) inside an otherwise legitimate-looking tool function.

Core Concept

When an MCP client sends a tool list to its language model, each tool is represented solely by its name, a natural-language description, and a JSON schema of accepted parameters. No source code is transmitted. The LLM decides whether to invoke a tool based entirely on this metadata, and the user typically approves based on the same limited information. This architecture creates a critical blind spot: the actual function body can contain any code, including subprocess calls, file system operations, network requests, or data exfiltration routines, all invisible to both the agent and the user. The threat is most severe under the stdio transport, where the MCP server process runs on the user's own machine with the same OS-level permissions as any local program. Code executed via stdio can read and write files, access environment variables (including API keys and credentials), and make outbound network connections. A tool that appears to "get weather data" or "multiply two numbers" can simultaneously run shell commands, create log files containing stolen data, or delete critical files. The user sees only the tool's return value, which can be perfectly correct, while the side effects remain completely hidden.

Key Points

  • Tool calls sent to the LLM contain only metadata (name, description, parameter schema), never implementation code.
  • A malicious tool can perform harmful side effects (shell commands, file writes, data exfiltration) while returning a correct, expected result.
  • Stdio transport is the highest-risk vector because the server code runs locally with the user's full OS permissions.
  • Installing an unvetted MCP server is equivalent to downloading and executing an unsigned binary from the internet.
  • Input data sent to a tool can be leaked by the malicious implementation to external servers or local log files.

Lesson 59: What is OAuth

OAuth 2.1 is a delegated authorization protocol where the MCP client follows a multi-step 'breadcrumb trail' of well-known endpoints to discover the authorization server, register itself, authenticate the user, obtain scoped tokens, and present them to the MCP server for validated access.

Core Concept

OAuth 2.1 is the officially mandated authentication standard for MCP. At a high level, it is a protocol that allows a client (the MCP agent) to obtain limited, scoped access to a server's resources on behalf of a user, without the user sharing credentials directly with the client. The flow begins when the MCP client attempts to connect to the MCP server and receives a 401 Unauthorized response. This response includes a header pointing to a well-known metadata endpoint (e.g., /.well-known/oauth-protected-resource). The client follows this URL to discover the authorization server's location, supported methods, and available scopes. It then follows another breadcrumb to the authorization server's own well-known configuration (/.well-known/openid-configuration), which provides endpoints for client registration, authorization, and token exchange. The client dynamically registers itself with the authorization server, receiving a client_id. It then redirects the user to the authorization server's login page, where the user authenticates (via username/password, Google login, etc.) and consents to the requested scopes (e.g., 'search:read'). Upon successful authentication, the authorization server issues an authorization code, which the client exchanges for an access token (JWT). The client stores this token and includes it as a Bearer token in subsequent requests to the MCP server. The MCP server validates the token's signature, issuer, audience, and scopes before allowing the tool call to proceed.

Key Points

  • OAuth 2.1 enables delegated authorization: the user authenticates once, and the client receives a scoped token to act on their behalf.
  • The flow starts with a 401 response containing a pointer to the well-known metadata endpoint.
  • The client follows a breadcrumb trail: resource metadata, then authorization server configuration, then registration, then login.
  • Dynamic client registration allows any compliant MCP client to register with any compliant server without pre-configuration.
  • Scopes (e.g., 'search:read') define what operations the token authorizes, enabling fine-grained access control.
  • The final access token is a JWT (JSON Web Token) containing the issuer, audience, scopes, and a cryptographic signature.

Lesson 60: OAuth 2.1 Workflow

Walking through the OAuth 2.1 flow manually (as if impersonating the MCP client) reveals the exact sequence of HTTP calls, redirects, and token exchanges that happen automatically when a compliant client authenticates with a protected MCP server.

Core Concept

To demystify OAuth 2.1, it is instructive to manually execute each step that an MCP client performs automatically. Starting with the MCP Inspector connected to a protected server, the first tool call returns a 401 Unauthorized response. The response headers contain a resource metadata URI pointing to /.well-known/oauth-protected-resource on the MCP server. Calling this endpoint returns a JSON document containing the authorization server's URL, the supported authentication method (Bearer), the resource identifier, and the available scopes (e.g., 'search:read'). The client then follows the authorization server URL to its /.well-known/openid-configuration, which provides the registration endpoint, authorization endpoint, and token endpoint. The client registers itself at the registration endpoint, receiving a client_id. It then constructs an authorization URL with parameters including response_type=code, the client_id, a redirect_uri, the requested scope, and a state parameter for CSRF protection. Opening this URL in a browser presents the user with a login page. After authentication (e.g., via Google), the user is redirected back with an authorization code. The client exchanges this code at the token endpoint for a JWT access token. This token is then included as a Bearer header in subsequent MCP requests, which the server validates. The entire process, while complex when traced manually, happens transparently and in seconds when performed by a compliant MCP client.

  • The authorization server's openid-configuration exposes registration, authorization, and token endpoints.
  • Client registration is dynamic: the client sends its redirect_uri and receives a client_id without human intervention.
  • The authorization URL includes response_type=code, client_id, redirect_uri, scope, and a state parameter for CSRF protection.
  • The complete flow, though multi-step, executes transparently in seconds when handled by a compliant client.

Lesson 65: Token Validation

Token validation verifies the JWT's cryptographic signature, issuer, audience, and required scopes using the ScaleKit SDK, with scope checking applied only to tool call requests to allow unauthenticated session initialization.

Core Concept

After the middleware confirms that a Bearer token is present, the next step is validating that the token is legitimate, unmodified, and authorized for the requested operation. JSON Web Tokens (JWTs) contain three parts: a header (algorithm and type), a payload (issuer, audience, scopes, expiration, and other claims), and a cryptographic signature. Validation must verify all three. The ScaleKit SDK simplifies this to a single method call: `validate_token(token, validation_options)`. The validation options specify the expected issuer (the ScaleKit environment URL), the expected audience (the MCP server's resource name, including the trailing slash), and optionally the required scopes. The SDK verifies the JWT signature against ScaleKit's public keys, checks that the issuer and audience match, validates the expiration, and confirms that the token contains the required scopes. An important nuance is that scope validation should only be applied to tool call requests, not to all MCP requests. MCP clients may connect to the server for session initialization or capability discovery before making tool calls. To distinguish tool calls, the middleware parses the request body and checks if the JSON-RPC method field indicates a tool invocation. If it is a tool call, the required scope (e.g., 'search:read') is added to the validation options. If it is a non-tool request, validation proceeds without scope checking. If `validate_token` succeeds, the request passes through to the MCP handler. If it raises an exception (invalid signature, wrong issuer, missing scope, expired token), the middleware catches it and returns a 401 error.

Key Points

  • JWTs contain three parts: header (algorithm), payload (issuer, audience, scopes, expiration), and cryptographic signature.
  • ScaleKit's validate_token() verifies signature, issuer, audience, expiration, and scopes in a single call.
  • The expected audience must exactly match the server's resource name, including the trailing slash.
  • Scope validation is applied only to tool call requests, not to session initialization or capability discovery.
  • Tool calls are identified by parsing the request body's JSON-RPC method field.
  • Failed validation raises an exception caught by the middleware, which returns a 401 error.

Lesson 70: RAG Pipeline

The quality of the final answer depends heavily on two earlier decisions: chunk size (too large loses precision; too small loses context) and embedding model quality (determines how well meaning is captured in the vector space).

Lesson 71: Embeddings

Embeddings are high-dimensional numerical vectors that capture semantic meaning, allowing text similarity to be measured by geometric distance rather than keyword overlap.

Core Concept

An embedding is a mapping from human-readable data (text, images, audio) into a point in a high-dimensional numerical space, where each dimension captures some facet of meaning. Conceptually, two dimensions might represent 'positivity' and 'topic relevance,' but real embedding models use thousands of dimensions (OpenAI's text-embedding-3-small uses 1,536 dimensions) to capture nuanced semantic relationships. The power of embeddings lies in the geometric property that semantically similar content maps to nearby points. 'The cat sat on the mat' and 'A feline rested on the rug' would have vectors close together in embedding space despite sharing zero keywords. This is what enables semantic search: instead of matching exact words, the system measures vector distance (typically cosine similarity) to find the most relevant content. Embedding models are distinct from generative LLMs; they are specialized neural networks trained specifically to produce meaningful vector representations, not to generate text.

Key Points

  • Embedding models are separate from generative LLMs; they are specialized for representation, not text generation.
  • Distance metrics like cosine similarity quantify how related two pieces of text are in embedding space.

Lesson 72: Vector Databases

Core Concept

After embedding text chunks into numerical vectors, those vectors need a storage system that can efficiently perform nearest-neighbor searches across potentially millions of entries. A regular database could store vectors as arrays, but it lacks the indexing structures needed for fast similarity search. The query workflow is straightforward: a user's question is embedded into the same vector space, and the database returns the k vectors closest to it (by cosine similarity, Euclidean distance, or dot product). Each returned vector is linked back to its original text chunk and metadata, providing the retrieval step of RAG. Popular vector databases include ChromaDB (lightweight, local-first, open source), Pinecone (managed cloud service), Weaviate, Qdrant, and Milvus. ChromaDB is particularly well-suited for prototyping and small-to-medium workloads because it requires no server setup and includes a built-in default embedding model.

  • ChromaDB is open source, runs locally, and includes a default embedding model, making it ideal for prototyping.

Stdio-based MCP servers communicate via standard input/output and require the client and server to run on the same machine. Remote MCP servers use HTTP, making them accessible over a network. The conversion has three steps. First, the MCP server logic (tool definitions) is separated into its own module (e.g., genius.py) rather than being the application entry point. Second, a FastAPI application is created in main.py that serves as the HTTP host. Third, the MCP server is mounted onto the FastAPI app at a specific route (typically /mcp) using FastMCP's integration with ASGI frameworks. This means the MCP protocol messages are handled at the /mcp endpoint while the FastAPI app can simultaneously serve other HTTP endpoints (health checks, metadata, etc.). The start command changes from 'python server.py' (stdio) to 'uvicorn main:app --host 0.0.0.0 --port 10000' (HTTP).

Key Points

  • Separate MCP tool definitions from the HTTP application entry point into distinct modules.
  • Create a FastAPI app in main.py and mount the MCP server at a route like /mcp.
  • FastMCP integrates with ASGI frameworks (FastAPI/Starlette) for HTTP transport.
  • The MCP endpoint (/mcp) coexists with other HTTP routes on the same FastAPI application.
  • The start command becomes 'uvicorn main:app --host 0.0.0.0 --port 10000' for network access.

Lesson 90: Add Auth to MCP Server

OAuth 2.1 authentication is added to the MCP server using ScaleKit SDK, with a settings validation object for environment variables and an auth middleware that verifies bearer tokens before allowing tool access.

Core Concept

Securing a remote MCP server requires authentication so that only authorized clients can invoke tools. The implementation uses ScaleKit, an OAuth 2.1 provider that handles the complexity of token issuance, validation, and client registration. The setup involves three components. First, a Settings class (using Pydantic or a simple dataclass) validates that all required environment variables are present at startup: the GNews API key, ScaleKit client ID, client secret, and environment URL. Second, an auth.py module initializes the ScaleKit SDK and defines a token verification function that extracts the bearer token from incoming requests, validates it against ScaleKit's servers, and checks that the token includes the required permissions (e.g., 'gnews:read'). Third, this auth function is registered as middleware on the FastAPI application, intercepting all requests to the /mcp endpoint. ScaleKit SDK version 2.3.2 or later is required for full MCP authentication support.

Key Points

  • ScaleKit provides OAuth 2.1 infrastructure: token issuance, validation, and dynamic client registration.
  • A Settings class validates all required environment variables at startup (fail-fast pattern).
  • The auth middleware intercepts MCP requests, extracts bearer tokens, and validates them via ScaleKit.
  • Permissions (scopes) like 'gnews:read' control fine-grained access to specific tools.
  • ScaleKit SDK >= 2.3.2 is required for MCP-compatible authentication features.

Lesson 91: Register on ScaleKit

The MCP server is registered in ScaleKit's dashboard by defining a server name, resource identifier (the deployment URL), and permissions, which generates the client credentials and OAuth metadata endpoint needed for the auth flow.

Core Concept

ScaleKit requires each MCP server to be registered as a protected resource. The registration process in ScaleKit's dashboard involves three pieces of configuration: a server name (e.g., 'GNews'), a resource identifier (the URL where the server is hosted, initially localhost for development), and a list of permissions/scopes that clients can request (e.g., 'gnews:read'). Dynamic client registration must be enabled so that MCP clients can automatically register themselves during the OAuth flow. After registration, ScaleKit provides the client ID, client secret, and environment URL that the server uses to validate tokens. The server must expose a well-known OAuth metadata endpoint (/.well-known/oauth-protected-resource/mcp) that returns the resource metadata, allowing MCP clients to discover the authentication requirements automatically. When deploying to production, a new server registration (or update) is needed with the production URL replacing localhost.

Key Points

  • Enable dynamic client registration so MCP clients can self-register during the OAuth flow.

  • The server must serve /.well-known/oauth-protected-resource/mcp for OAuth discovery.
  • A separate registration (or update) is needed for production URL vs. localhost.

Lesson 93: Deploy to Render

Deploying to Render involves creating a Web Service, connecting the GitHub repository, setting the build command to 'uv sync' and the start command to 'uvicorn main:app', configuring environment variables, and specifying host 0.0.0.0 with port 10000.

Core Concept

The Render deployment process connects the GitHub repository to a new Web Service. After signing in and granting Render access to the specific GitHub repository, the configuration requires four key settings. Third, environment variables from the local .env file are added through Render's dashboard (Settings > Environment). Fourth, the runtime is set to Python with the correct branch (master/main). Once deployed, Render provides a public URL (e.g., demo-gnews-remote-mcp.onrender.com) that serves as the MCP server's permanent address.

  • Port 10000 is Render's default; the app must listen on this port.
  • Environment variables are configured in Render's dashboard, not in the repository.
  • Render auto-deploys on each push to the connected branch.
