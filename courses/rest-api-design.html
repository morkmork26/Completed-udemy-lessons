Lesson 7: What Is an API?

An API (Application Programming Interface) is a set of clearly defined methods that allow software components to communicate with each other, analogous to how a user interface exposes functionality to humans.

Core Concept

API as a software interface

Key Points

  • API stands for Application Programming Interface
  • Wikipedia definition: 'a set of clearly defined methods of communication among various components'
  • A user interface exposes functionality visually to humans; an API exposes functionality programmatically to applications
  • The word 'exposed' is critical: an API defines what is visible and accessible to external consumers
  • API content (URLs, JSON, parameters) is designed for machine consumption, not human readability
  • The address line of an API request (the URL) is the primary element REST API design focuses on

  • Understanding the UI analogy clarifies API design: just as good UI design makes apps intuitive for users, good API design makes integration intuitive for developers

Lesson 8: API Types

APIs exist in four major categories (Operating System, Library, Remote, and Web), each serving a different integration scope, with Web APIs being the most widely used and the focus of REST design.

Core Concept

The four API categories

Key Points

  • Operating System API: applications request OS services (file system, network devices, UI elements) through the OS API; Win32 API is the most well-known example
  • Library API: reusable code packages expose functionality through APIs; examples include jQuery for DOM manipulation and Apache Commons for Java utilities
  • Remote API: enables communication between applications on different machines; RMI (Remote Method Invocation) in Java and DCOM in Windows are classic examples
  • Web API: the most common type today; uses standard web protocols (primarily HTTP) to enable cross-platform, cross-network communication
  • Web APIs are the broadest and most platform-agnostic category, which is why REST API design focuses here

Operating System API

Apps request OS services (files, network, UI). Example: Win32 API on Windows.

Library API

Code packages expose reusable functionality. Example: jQuery, Apache Commons.

Remote API

Cross-machine communication between apps. Example: Java RMI, Windows DCOM.

Web API

HTTP-based, platform-agnostic communication. The dominant API type today and the basis for REST.

💡 Operating System API
When an application displays a button on Windows, it calls the Win32 API to request the OS to render that UI element.
💡 Library API
A JavaScript developer calls jQuery's $.ajax() method; this is consuming the jQuery library's API.
💡 Remote API
Java RMI allows one JVM to invoke methods on an object residing in another JVM on a different machine.
Key Takeaways
  • Each API type serves a progressively wider integration scope: same-machine OS calls, same-process libraries, cross-machine remote calls, and finally cross-network web APIs
  • Web APIs subsume much of what Remote APIs once did, with the added benefit of platform independence and HTTP standardization

Lesson 9: Importance of API

APIs are essential because modern architectures (mobile apps, SPAs) require them to communicate with backend servers, and they also enable business extension and monetization.

Core Concept

APIs as business and architectural necessities

Key Points

  • Single Page Applications (SPAs) built with React, Angular, or Vue render on the client and must call server APIs for data
  • APIs extend an application's reach by allowing third-party developers to build on top of the platform
  • APIs enable monetization: companies can charge for API access (per-call pricing, subscription tiers)
  • Twitter is a classic example: it became a platform rather than just a website because its API let thousands of third-party apps interact with it
  • Without an API, a backend application is isolated and limited to whatever frontend the developer builds

Mobile Access

SPA Architecture

Modern frontend frameworks (React, Angular, Vue) render client-side and depend entirely on API calls for data.

Platform Extension

APIs let third-party developers build on top of a service, multiplying its reach beyond what one team could build.

Monetization

API access can be sold per-call or by subscription, turning backend capabilities into direct revenue.

  • An API is not optional in modern architecture; it is the mandatory communication channel between any client (mobile, SPA, third-party) and the server
  • APIs transform products from isolated applications into extensible platforms with monetization potential

Lesson 12: Web APIs

Web APIs are platform-agnostic interfaces that use standard HTTP protocols in a request/response model, differentiated primarily by their request and response formats and content.

Core Concept

Web API characteristics and differentiation criteria

Key Points

  • Definition: an API exposed by a web component that allows other components to interact with it over the network
  • Platform agnostic: a .NET component can communicate with a Python component seamlessly through a web API
  • Standard protocols: almost all web APIs operate over HTTP
  • Request/response paradigm: a client sends an HTTP request and receives an HTTP response
  • Web API types are differentiated by four axes: request format, request content, response format, and response content
  • The four major web API types are SOAP, REST, GraphQL, and gRPC

💡 Cross-Platform Communication
A .NET microservice sends an HTTP request to a Python service's web API. Neither service needs to know the other's implementation language; HTTP and JSON serve as the universal contract.
Key Takeaways
  • Platform agnosticism is the defining advantage of web APIs over OS, library, or remote APIs
  • When evaluating or comparing web API types, focus on the four differentiation axes: request format, request content, response format, response content

Lesson 13: SOAP

SOAP (Simple Object Access Protocol) is an XML-based, RPC-style web API from 1998 that is extensible but largely outdated, suitable only for legacy system integration.

Core Concept

SOAP protocol fundamentals

Key Points

  • SOAP stands for Simple Object Access Protocol, designed in 1998 for Microsoft
  • XML-based protocol: both requests and responses use strict XML formatting
  • Uses RPC (Remote Procedure Call) style: clients invoke specific named methods on the server
  • Extensible: the base protocol can be extended for authentication, routing, transactions, and federation
  • Request structure: an XML envelope containing metadata and a body that specifies the method name and parameters
  • Considered outdated; should only be used when interfacing with legacy systems that expose only SOAP endpoints
💡 SOAP Stock Price Request
A SOAP request wraps the method call 'GetStockPrice' with parameter 'StockName=IBM' inside an XML envelope with a body element. The strict XML structure contrasts sharply with REST's simpler URL+JSON approach.
Key Takeaways
  • SOAP's XML verbosity and RPC coupling made it powerful but complex; REST replaced it by favoring simplicity and resource-oriented design
  • SOAP knowledge remains relevant only for legacy integration scenarios

Lesson 14: REST

REST (Representational State Transfer) is a message-style web API based on URLs and JSON, designed in 2000 by Roy Fielding, that became the de facto standard because of its simplicity: send to a URL, get back JSON.

Core Concept

REST as the dominant web API paradigm

Key Points

  • REST stands for Representational State Transfer, designed by Roy Fielding in 2000
  • Based on URL + JSON: no XML envelopes, no complex schemas
  • Message-style protocol: clients send messages to URLs rather than calling specific methods (contrast with SOAP's RPC style)
  • The URL endpoint determines what operation to perform based on the HTTP verb and the message content
  • De facto standard: virtually all major websites expose REST APIs
  • Simplicity is REST's primary advantage over SOAP, GraphQL, and gRPC
💡 REST vs SOAP Simplicity
To get a stock price via SOAP, a client constructs an XML envelope calling 'GetStockPrice'. Via REST, the client simply sends GET /api/stocks/IBM and receives a JSON response. The reduction in ceremony is dramatic.
Key Takeaways
  • REST's dominance stems from its radical simplicity: URL + JSON eliminated the XML overhead and RPC coupling that made SOAP burdensome
  • Message-style design decouples clients from server internals; the URL and HTTP verb convey intent without exposing method names

Lesson 15: GraphQL

GraphQL enables clients to specify exactly which fields they need in a single query, eliminating over-fetching and under-fetching, but requires more upfront development effort and can suffer from performance issues compared to REST.

Core Concept

GraphQL flexible querying

Key Points

  • Developed internally by Facebook in 2012, publicly released in 2015
  • Clients define the exact fields they want in the query, solving the over-fetching problem where REST returns entire entities
  • Supports querying, updating (mutations), and subscribing to real-time data changes
  • JSON in, JSON out: same transport format as REST
  • Queries can traverse relationships (e.g., fetching a post's author name in the same query)
  • Disadvantages: requires significant upfront development effort and can be less performant than REST due to query complexity
  • Performance issues arise because the server must dynamically resolve arbitrary query shapes rather than serving pre-optimized endpoints
💡 GraphQL Field Selection
A query for 'posts' specifies only id, title, body, publishDate, and author.name. The response contains exactly those fields, nothing more. A REST equivalent would return the entire post object including fields the client does not need.
Key Takeaways
  • GraphQL trades REST's simplicity for query precision; the right choice depends on whether the application's data access patterns are complex enough to justify the overhead
  • The subscription capability for real-time data updates is a unique strength not available in standard REST

Lesson 16: gRPC

gRPC, built on HTTP/2 and Protocol Buffers, delivers high-performance bidirectional streaming but requires specialized libraries on both ends and has not yet achieved widespread adoption.

Core Concept

gRPC high-performance streaming API

Key Points

  • Developed by Google in 2015, built on HTTP/2
  • HTTP/2 enables bidirectional streaming: the server can push messages to the client, not just respond to requests
  • Uses Protocol Buffers (protobuf) instead of JSON or XML for serialization, providing compact binary encoding
  • Code generators read protobuf definitions and generate platform-specific classes (.NET, Java, etc.)
  • Performance is excellent due to binary encoding and HTTP/2 efficiency
  • Adoption is limited: HTTP/2 is still not universally deployed, and protobuf requires tooling at both client and server
  • Not suitable for browser-based clients without additional proxy layers

Lesson 17: What is REST?

REST (Representational State Transfer) means that a client requests a resource's current state from a server and receives back a representation of that state, typically as JSON.

Core Concept

Representational State Transfer explained

Key Points

  • REST stands for Representational State Transfer; each word carries specific meaning
  • State: the current properties of a resource, or the result of an action performed on it
  • Representation: the format in which the state is encoded and transmitted (usually JSON)
  • Transfer: the state representation moves from server to client (or confirmation of an action moves back)
  • Request/response model: client sends a request specifying a resource, server returns a representation of that resource's state
  • For retrieval (GET): the response contains the resource's current property values as JSON
  • For actions (DELETE, PUT): the response contains a representation confirming the action's result, not necessarily the resource data itself

Resource

Any entity the API manages: an order, a user, a product. Identified by a unique URL.

State

The current properties of a resource (for reads) or the outcome of an action on it (for writes/deletes).

Representation

The format encoding the state for transport. Almost always JSON; occasionally XML or HTML.

Transfer

The movement of the state representation between client and server over HTTP.

💡 GET Order State
Client requests GET /orders/17. The server returns a JSON representation of order 17's state: order date, customer, and line items. The JSON is the 'representation' of the 'state' being 'transferred'.
💡 DELETE Action Result
Client requests DELETE /orders/17. The server returns a representation confirming deletion succeeded. The 'state' here is the result of the delete action, not the order's properties.
Key Takeaways
  • The name 'Representational State Transfer' is not arbitrary jargon; it precisely describes the mechanics: transfer a representation of a resource's state
  • REST treats everything as a resource with state, and every API interaction is about transferring a snapshot of that state in a standard representation format

Lesson 18: Structure of REST API Request

A REST API request consists of four components: the HTTP method (verb) that declares intent, the URL that locates the resource, headers that carry metadata, and an optional body that contains the request payload.

Core Concept

REST request anatomy

Key Points

  • Method (HTTP verb): GET, POST, PUT, DELETE; each verb has a specific, well-defined role
  • URL: the address of the resource, optionally including query parameters
  • Headers: metadata about the request (User-Agent, Authorization, Cache-Control, Host, Content-Type)
  • Body: the content/payload of the request; optional and not present in all request types (e.g., GET typically has no body)
  • The verb + URL combination is the most critical part; it declares what action to perform on which resource

Carry metadata: authentication tokens, content type, caching directives, client identity

Contains the request payload (e.g., JSON data for POST/PUT). Omitted for GET and DELETE.
💡 Anatomy of a GET Request
Method: GET | URL: /api/orders/17 | Headers: User-Agent, Host, Cache-Control | Body: (none). The verb declares read intent, the URL identifies the resource, and headers provide context. No body is needed for a retrieval.
Key Takeaways
  • The four request components map to a simple question: What do you want to do (method), to which resource (URL), with what context (headers), carrying what data (body)?
  • GET requests typically omit the body; the URL alone identifies the resource to retrieve

Lesson 19: Structure of REST API Response

A REST API response contains three components: a numeric status code indicating success or failure, headers with response metadata, and an optional body carrying the resource's state representation (usually JSON).

Core Concept

REST response anatomy

Key Points

  • Status Code: a three-digit number indicating the outcome (e.g., 200 = OK, meaning the request succeeded)
  • Headers: metadata about the response (content type, caching, server info)
  • Body: the response payload containing the resource's state representation; optional and not always present
  • JSON is the standard response format; XML and HTML are alternatives but rarely used
  • The response body for a GET request contains the resource data; for other methods it may contain confirmation or be empty
  • Always default to JSON unless the client explicitly requires a different format
1
1. Status Code
Three-digit number: 2xx = success, 4xx = client error, 5xx = server error
2
2. Headers
Response metadata: content type, cache directives, rate-limit info
3

The state representation, typically JSON. May be absent for DELETE confirmations or 204 responses.
💡 200 OK Response for Order
Status: 200 | Headers: Content-Type: application/json | Body: {"orderNumber": 17, "orderDate": "2023-01-15", "items": [...]}. The status confirms success, and the body carries the JSON representation of the order's state.
Key Takeaways
  • Request and response are symmetrical: both have headers and an optional body, but the response adds a status code while the request has a method
  • JSON should be the default representation format; deviate only when a client explicitly demands otherwise

Lesson 22: What is Postman?

Postman is the industry-standard REST API client that allows developers to construct requests (setting verb, URL, headers, body), send them, and inspect the full response (status, headers, body).

Core Concept

Postman as the standard API testing client

Key Points

  • Postman is the most popular REST API client tool in the industry
  • Core functionality: set HTTP verb, URL, headers, and body; send the request; view the complete response
  • Response inspection includes body content, headers, status code, response time, and response size
  • Extremely easy to learn; basic proficiency takes minutes
  • Advanced features available (collections, environments, automated testing, scripting) but not required for basic usage
Key Takeaways
  • Postman bridges the gap between API design and validation: it provides a visual interface to exercise every aspect of a REST API request and inspect every aspect of the response
  • While Beeceptor creates the mock API, Postman is the tool used to interact with it (and later, with real APIs)

  • The access token is the currency of OAuth: it encodes identity and permissions without transmitting raw credentials.

Lesson 58: The JWT

A JSON Web Token (JWT) is a compact, self-contained string composed of three Base64-encoded sections (Header, Payload, Signature) that carries user identity and permissions without requiring the server to query a database on every request.

Core Concept

JWT Structure and Purpose

Key Points

  • JWT stands for JSON Web Token. It is the standard access token format used with OAuth 2.0.
  • The Header contains the token type (JWT) and the signing algorithm (e.g., HS256).
  • The Payload contains the actual user data needed for authorization decisions: name, role, organization, and any custom claims. There is no enforced standard format.
  • The Signature is a cryptographic hash of Header + Payload + Secret. It prevents tampering during transit.
  • The token is encoded (Base64), not encrypted. Anyone can decode and read the payload. The signature only ensures integrity, not confidentiality.
  • The three sections are concatenated with dots: header.payload.signature

Header

Token type (JWT) and signing algorithm (e.g., HS256). Metadata about how to process the token.

Payload

User claims: identity, roles, permissions, and custom data. The core information the API needs for authorization.

Signature

HMAC hash of (Header + Payload + Secret). Ensures the token has not been modified in transit.

Encoding

All three parts are Base64-encoded and joined with dots. Readable by anyone; integrity (not secrecy) is the goal.

💡 JWT Header
{"typ": "JWT", "alg": "HS256"} specifies the token type and the HMAC-SHA256 signing algorithm.
💡 JWT Payload
{"name": "John Doe", "role": "admin", "sub": "1234567890"} carries the claims about the user that the API uses for authorization.
Key Takeaways
  • JWT is self-contained: the server can make auth decisions from the token alone, without a database lookup.
  • The signature guarantees integrity but not confidentiality; sensitive data should not be placed in the payload without additional encryption.
  • The payload format is flexible, but consistent claim naming across services simplifies authorization logic.

Lesson 59: JWT in REST API

In a REST API, the JWT is transmitted via the Authorization header using the Bearer scheme (Authorization: Bearer <token>), keeping auth data out of the URL and request body.

Core Concept

Sending JWT via REST API Headers

Key Points

  • The standard method for sending a JWT to a REST API is the Authorization header with the Bearer prefix: Authorization: Bearer <jwt>.
  • While technically possible to send a JWT in the request body or as a query parameter, both approaches are discouraged for security and convention reasons.
  • The API itself remains a transport mechanism; it passes the JWT to the backend code, which validates the signature and reads the payload.
  • The resource server checks the JWT signature for integrity, then reads the payload to determine the user's identity and permissions.
1
1. Obtain JWT
Client authenticates via OAuth 2.0 and receives a JWT from the authorization server.
2
2. Attach to Header
Client places the JWT in the Authorization header using the Bearer scheme.
3
3. API Receives
The REST API extracts the JWT from the header and passes it to backend code.
4
4. Validate & Authorize
Backend verifies the signature, reads the payload claims, and grants or denies access.

GET /api/v1/orders HTTP/1.1 | Host: example.com | Authorization: Bearer eyJhbGciOiJIUzI1NiIs... The JWT follows the 'Bearer' keyword in the Authorization header.
Key Takeaways
  • Always use the Authorization: Bearer header for JWT transmission. Avoid query strings (logged in server logs) and request bodies (semantically incorrect for GET requests).
  • The REST API is not the authentication engine; it is the delivery channel for the token.

Lesson 62: Async Operations

Asynchronous operations prevent threads from blocking on long-running I/O (file, database, network), freeing the web server to handle other requests concurrently and dramatically improving throughput.

Core Concept

Async/Await Pattern for I/O-Bound Work

Key Points

  • Synchronous code blocks the thread until an I/O operation completes; asynchronous code initiates the operation and continues executing other work.
  • This pattern is most relevant for I/O-bound operations: file reads, database queries, and network calls.
  • Almost every modern platform supports async patterns (async/await in JavaScript, C#, Python; coroutines in Kotlin, etc.).
  • Async operations free threads on the web server, allowing it to serve more concurrent requests with the same hardware.
  • The async keyword marks a function as asynchronous; the await keyword signals a non-blocking wait point within that function.

  • Always use async patterns for I/O operations in API code. Blocking threads under load causes cascading performance failures.
  • Async does not make individual operations faster; it makes the server more efficient by handling more requests concurrently.

Lesson 63: Caching

Caching stores frequently accessed data in-memory close to the API, eliminating repeated database/network round-trips, but requires deliberate expiration and invalidation strategies to prevent serving stale data.

Core Concept

In-Memory Caching with Expiration and Invalidation

Key Points

  • Caching places frequently accessed data in memory, avoiding expensive I/O operations on every request.
  • Cache engines (Redis, Memcached, in-process caches) store data in RAM for near-instant retrieval.
  • Expiration: cached data automatically expires after a predefined duration (e.g., 30 seconds, 5 minutes).
  • Invalidation: cached data is explicitly removed when the underlying source data changes (e.g., a new user is added to the system).
  • Stale data (cached data that no longer reflects reality) is the primary risk of caching and must be actively managed.
  • Response caching (e.g., ASP.NET ResponseCache) caches the entire API response on the web server for a set duration.
1
1. First Request
API receives a request, queries the database, and stores the result in the cache with an expiration time.
2
2. Cache Hit
Subsequent requests within the expiration window are served directly from in-memory cache, skipping the database.
3
3. Expiration
After the predefined duration, the cache entry expires. The next request triggers a fresh database query.
4
4. Invalidation
If the underlying data changes (write/update/delete), the cache entry is explicitly removed to prevent stale responses.
💡 ASP.NET ResponseCache
Applying [ResponseCache(Duration = 30)] to an API endpoint caches its response for 30 seconds. Subsequent requests within that window are served from cache, bypassing the database entirely.
💡 Invalidation Scenario
A cached user list becomes stale when a new user is added. The cache entry must be invalidated (deleted) upon user creation so the next request fetches the updated list from the database.
Key Takeaways
  • Caching is one of the highest-impact performance optimizations, but stale data is its primary pitfall.
  • Always implement both time-based expiration AND event-driven invalidation.

Lesson 64: Rate Limit

Rate limiting caps the maximum number of concurrent requests the API processes, returning a 'server too busy' response to excess traffic so the API remains operational for existing requests instead of crashing under overload.

Core Concept

Protecting API Availability with Rate Limiting

Key Points

  • Without rate limiting, a sudden traffic spike can overwhelm the API, causing a crash that affects all users.
  • A rate limiter sits in front of the API and enforces a maximum concurrent request threshold.
  • When the threshold is exceeded, additional requests receive a response code indicating the server is too busy (HTTP 429 Too Many Requests).
  • The API continues processing already-accepted requests normally; once those complete, it accepts new ones.
  • Rate limiting protects availability: it sacrifices some requests to keep the service alive for the majority.
1
1. Normal Traffic
Requests flow through the rate limiter to the API and are processed normally.
2
2. Threshold Reached
Incoming request count exceeds the configured maximum concurrent limit.
3
3. Excess Blocked
Rate limiter returns HTTP 429 (Too Many Requests) to new incoming requests.
4
4. Recovery
As in-flight requests complete, the API has capacity again and accepts new requests.
💡 Overload Protection
An API configured with a 1,000 concurrent request limit continues serving those 1,000 normally. Request #1,001 receives a 429 response and can retry after load decreases.
Key Takeaways
  • Rate limiting is a safety valve: it prevents total API collapse by gracefully rejecting overflow traffic.
  • HTTP 429 is the standard response code for rate-limited requests.

Lesson 65: Quota

Quotas limit the number of requests a specific client can make over a time window (per day, per second), preventing any single consumer from monopolizing API resources.

Core Concept

Per-Client Request Quotas

Key Points

  • Unlike rate limiting (which caps total API throughput), quotas cap individual client usage.
  • Quotas are defined per client, per time window: e.g., 50,000 requests per project per day, or 10 queries per second per IP address.
  • Multiple quota tiers can coexist (daily project-level cap + per-second IP-level cap).
  • Quotas minimize the risk of heavy load from a single consumer while preserving fair access for all clients.
  • Major API providers (Google, AWS, Twitter) publish quota definitions as part of their API documentation.

Lesson 70: HATEOAS

HATEOAS (Hypermedia As The Engine Of Application State) embeds links to related resources directly within API responses, so clients need only know the root endpoint and can discover all other resources by following links returned in each response.

Core Concept

Self-Describing APIs via Hypermedia Links

Key Points

  • HATEOAS stands for Hypermedia As The Engine Of Application State.
  • API responses include a 'links' section containing URLs to related resources (self, sub-resources, related entities).
  • Clients need zero prior knowledge of the API structure beyond the root endpoint; all navigation is driven by the links in responses.
  • This eliminates hard-coded URLs in client code, making the API more evolvable: endpoints can change without breaking clients.
  • Netflix's Genie (open-source job orchestration engine) implements HATEOAS in its REST API, embedding links to job status, output, execution, and related resources in every job response.
1
1. Root Request
Client calls the root endpoint (e.g., /api/v3/jobs/{id}). This is the only URL the client needs to know.
2
2. Response + Links
Server returns the resource data along with a 'links' section containing URLs to all related resources.
3
3. Client Navigates
Client selects the relevant link (e.g., 'status', 'output') from the response and follows it.
4
4. Deep Discovery
Each subsequent response also includes its own links, enabling unlimited depth of resource navigation.
💡 Netflix Genie API
A GET request to /api/v3/jobs/{id} returns the job entity plus a 'links' section with URLs for self, output, request, execution, status, and related sub-resources, all pre-constructed for the specific job ID.
💡 Following Links
After retrieving a job, a client wanting the job's status does not consult documentation. Instead, it reads the 'status' link from the response's links section and makes a GET request to that URL.
Key Takeaways
  • HATEOAS makes APIs self-documenting and resilient to URL changes, since clients follow links rather than constructing URLs.
  • Adoption is optional but particularly valuable for complex APIs with deep resource hierarchies.

Lesson 71: API Gateway & Discovery

API Gateway (centralized proxy) and Service Discovery (URL directory) both solve the 'spider web' coupling problem in microservices, where direct service-to-service communication creates fragile dependencies that break when any single URL changes.

Core Concept

Decoupling Microservices with Gateway and Discovery Patterns

Key Points

  • Direct service-to-service communication creates a 'spider web' of hard-coded URLs; changing one URL can break multiple services.
  • Service Discovery (e.g., Consul) acts as a Yellow Pages directory: services look up target URLs dynamically, so only the directory needs updating when a URL changes.
  • API Gateway acts as a middleman/proxy: services call the gateway, which maps tasks to internal URLs and forwards requests. Calling services never know the target URL.
  • API Gateway provides additional features beyond routing: authentication, authorization, monitoring, load balancing, and routing policies.
  • Discovery is simpler to implement but provides fewer features (mainly URL resolution and basic load balancing).
  • Both patterns reduce coupling from N-to-N (spider web) to N-to-1 (hub and spoke).
  • Cloud API Gateway options: Azure API Management, AWS API Gateway, Google Apigee. On-premises: WSO2, Tyk.

Six microservices with direct communication create 30 potential connections. Changing the Stock Service URL requires updating every service that calls it.

Key Takeaways
  • The spider web anti-pattern is a hallmark of tightly coupled microservices; Gateway or Discovery is the remedy.
  • Choose Gateway for rich cross-cutting features (auth, monitoring, load balancing); choose Discovery for simplicity and speed of setup.
  • API Gateway is not mandatory but should be an informed architectural decision, not an afterthought.
